1. High-level architecture
Single unified binary that embeds two logical subsystems:

Metadata service (Raft): small replicated state machine storing cluster membership, epoch numbers, mapping overrides, and administrative commands. Use Raft to decide membership and epoch transitions so there’s a single source of truth. 

Data service (consistent hashing): each process participates in a hash ring (with virtual nodes) to own bulk key ranges and serve reads/writes for those keys. The ring is derived from the Raft-backed membership and epoch. 

Client library / proxy: clients consult the metadata (cached epoch + ring snapshot) and then talk directly to data nodes for bulk operations; metadata writes (e.g., create table, change replication factor) go through the Raft leader.

2. Core protocol ideas and epoch model
Epochs as authoritative cutover points. The Raft log records epoch changes: Epoch N -> Epoch N+1 with the full membership list and ring seed. Once an epoch entry is committed, all nodes must treat that epoch as authoritative for routing and rebalancing.

Two-phase cutover for reconfiguration

Commit epoch in Raft (metadata authoritative). 

Background data movement: nodes stream keys to new owners according to the new ring while both old and new owners accept reads/writes for keys tagged with the new epoch. Clients switch to the new epoch after seeing the committed epoch id.

Mapping overrides: small, Raft-backed exceptions for hot keys or manual pinning. These are cheap to replicate and give operational control.

3. Read/write flow and consistency model
Writes (strong metadata guarantees, tunable data guarantees):

Metadata-affecting ops (create namespace, change replication factor) are appended to Raft and only take effect once committed. This gives linearizable metadata semantics. 

Bulk data writes: client hashes key → finds owner(s) from cached ring for current epoch → sends write to owner(s). Replication among owners can be synchronous (wait for majority of replicas for strong durability) or asynchronous for higher throughput.

Reads:

Fast path: read from the primary owner for the key (as determined by ring). Optionally read-repair or quorum reads for stronger consistency.

Read-after-write: ensure client sees epoch committed and either read from leader-replicated primary or use a quorum read to guarantee visibility.

Guarantees:

Metadata: linearizable via Raft. 

Data: choose between eventual, quorum, or primary-acknowledged strong durability depending on replication strategy.

4. Failure modes and operational pitfalls
Leader bottleneck for metadata: Raft leader handles all metadata writes; keep metadata small and batched. Use snapshots and compaction to bound Raft log size. 

Split brain / stale ring snapshots: clients or nodes using stale epoch/ring can misroute. Mitigation: include epoch id in every client request; reject requests for older epochs and return the committed epoch id so clients refresh.

Rebalance storms: naive rehashing moves many keys. Use virtual nodes, rate-limited streaming, and prioritized hot-key pinning to reduce impact. Consistent hashing minimizes remapping but does not eliminate data movement. 

Concurrent membership changes: serialize via Raft — only one epoch change committed at a time. If you allow multiple simultaneous reconfigs, you must implement a deterministic merge or reject concurrent proposals.

Data loss during partial rebalancing: ensure that ownership transfer uses a handshake: source streams data and a final transfer marker is committed or acknowledged; until that marker, both old and new owners accept reads/writes (dual-write) to avoid gaps.

Network partitions: Raft requires a majority for progress; during minority partitions, metadata changes stall but data reads from existing owners can continue if you accept stale reads. Design your availability/consistency tradeoffs explicitly.

Ring representation: store the ring seed and virtual-node mapping in Raft metadata as a compact descriptor (not full per-key map). Nodes compute the ring locally from the descriptor.

Epoch identifier: use a monotonically increasing integer plus Raft term to avoid ambiguity.

Snapshotting: snapshot Raft state frequently; store compacted membership + ring descriptor in snapshot to speed recovery. 

Data transfer protocol:

Streaming with checksums and per-chunk acknowledgements.

Transfer marker: after streaming, source writes a Raft metadata entry marking completion for that key-range/epoch so the system can GC old copies.

Hotspot mitigation: support virtual nodes, replication factor tuning, and client-side caching. Consider rendezvous hashing if you want simpler rebalancing semantics for certain workloads. 

Single binary advantages: simpler deployment, fewer moving parts, consistent logging and metrics. Downsides: larger binary surface, more complex testing matrix for combined behaviors.

Goal: move ownership for affected key ranges from old owners to new owners without blocking the control-plane timers or starving the data-plane event loops.
Approach: treat an epoch transition as a non-blocking, Raft-committed cutover followed by incremental streaming transfers and a small, Raft-backed finalization marker that permits safe GC. This separates decision (Raft) from work (streaming) and keeps the control plane responsive. 

Data transfer protocol (practical recipe)
Commit epoch descriptor in Raft. The committed entry contains the new membership, ring seed, and a transfer plan (ranges or vnode lists).

Dual-accept window. After commit, both old and new owners accept reads/writes for keys in the affected ranges and tag every operation with the epoch id. Clients may continue using the old epoch until they observe the committed epoch id.

Incremental streaming with checksums and chunk ACKs. Source nodes stream chunks to targets with per-chunk checksums and acknowledgements. Stream at a controlled rate and resume on failure. This avoids large blocking transfers and enables resume semantics. 

Finalization marker in Raft. When a target has fully received and validated a range, it requests a small Raft entry marking that range as transferred for epoch N. Once that entry is committed, the source can stop accepting writes for that range and GC local copies. This gives a single linearizable point to reclaim storage. 

I/O and event-loop isolation

Graceful client cutover: clients may continue to use the old owner until they observe the committed epoch; once they see the new epoch, they switch to the new owner. During the dual-accept window both owners accept requests, and the transfer protocol ensures no gaps.

3. The Architectural Friction Point: Dual-Accept Reconciliation
The most dangerous edge case in this specification lives in Step 2: Dual-write reconciliation.

During the dual-accept window, allowing both the old owner and the new owner to accept writes for the same key introduces a severe consistency trap. If you rely on "last-writer-wins" (LWW) using standard system clocks, clock drift between the two nodes could cause a newer write on the old owner to be silently clobbered by a slightly older write on the new owner during the chunk streaming phase.

To maintain the strict consistency guarantees that HashRaft promises, you generally have two paths here:

Hybrid Logical Clocks (HLCs): Every Raft message and client request must carry a logical timestamp, ensuring that even if physical clocks drift, causality is perfectly preserved during reconciliation.

Write Proxying: Instead of true dual-accept for writes, the new owner accepts the write but immediately proxies it back to the old owner (the source of truth for the previous epoch) until the finalization marker is committed. This enforces a single serialization point for the key range during the vulnerable transition window.

Streaming and incremental reconciliation

Old owner streams chunks to new owner. Each chunk includes per-key HLC timestamps and checksums. New owner applies chunks only if the incoming HLC is newer than its local version.

If a write arrives at the new owner during streaming, the new owner compares HLCs: if the incoming client write HLC is newer than the streamed chunk, the new owner keeps the client write; otherwise it keeps the streamed value. HLC ensures deterministic ordering.

Finalization marker

Once new owner has validated all chunks and reconciled writes deterministically, it requests a Raft entry marking the range transferred. After commit, old owner revokes the lease and GC is allowed.

Conflict resolution rules and guarantees
Causality via HLC

All client writes carry an HLC timestamp derived from the client’s last-seen HLC and the node’s physical clock. HLCs are monotonic and preserve causality even with clock skew.

During reconciliation, compare HLCs to pick the winner deterministically.

Lease as single-writer guarantee

Deterministic tie-breaker

If HLCs are equal (rare), use a deterministic tie-breaker: (epoch id, node id) lexicographic order. This is stable and reproducible across nodes.

Idempotency and resumability

Streaming chunks are idempotent and include per-key sequence or HLC so replays do not corrupt state. Transfer cursors persist across restarts.

Concurrent multi-key transactions

Transfer Token Structure (canonical fields)
Each transfer token is a compact, signed descriptor issued as part of the Raft-committed epoch entry (or derived deterministically from it). Store the token in Raft metadata and include it in RPCs during transfer.

Token fields (one-line per field)

epoch_id: monotonic epoch integer.

range_id: canonical identifier for the key-range or vnode list.

transfer_nonce: cryptographically random 128-bit nonce unique per transfer.

lease_hint_hlc: HLC timestamp hint used to bound lease validity.

lease_duration_ms_hint: suggested lease duration in milliseconds.

finalization_marker_id: Raft log index or UUID that will be written when transfer completes.

signature: HMAC-SHA256 over the token fields using the cluster signing key (stored in Raft or derived from Raft keys).

Representation example (compact wire form):
token = base64(epoch_id || range_id || nonce || lease_hint_hlc || lease_duration_ms_hint || finalization_marker_id || signature)

Lease renewal

The old owner may renew the lease locally while streaming; renewals are local and do not require Raft. Renewals are only valid if the Raft epoch has not advanced past the token’s epoch_id. If Raft commits a newer epoch that supersedes the transfer plan, the lease is considered revoked.

Write acceptance rules (arrival-time checks)
When a write arrives at any node (old owner, new owner, or proxy), apply these checks in order:

Verify token signature if the write carries a transfer token. Reject if invalid.

Check epoch vs committed epoch: if write.epoch_id < committed_epoch, reject and return committed epoch.

HLC monotonicity: require write.hlc >= node.last_seen_hlc (update last_seen_hlc on acceptance).

Finalization check: if finalization_marker_id for range_id is committed in Raft and write.hlc <= finalization_hlc (the HLC recorded with the finalization commit), reject as stale.

Lease-holder check:

If old owner holds a valid lease (token epoch matches committed epoch and lease not expired), accept and serialize locally.

If new owner receives a write for a range under transfer and the lease is still valid, proxy the write to the old owner (fast async dispatch) or return a retry-with-owner response.

Idempotency guard: every write must carry a client_write_id (UUID) and HLC. If the write id has been applied with an equal-or-later HLC, treat as idempotent and return success without reapplying.

Key invariant: no write with HLC ≤ finalization_hlc can change state after finalization.

Proxying and delayed messages handling
Proxy behavior: new owner proxies writes to old owner including the original client HLC and client_write_id. Old owner applies and returns an ack; proxy forwards ack to client. Proxy timeouts must be short; on timeout return a retry suggestion.

Delayed proxyed write: if a proxied write is delayed and arrives at old owner after finalization commit:

Old owner checks write.hlc vs finalization_hlc. If write.hlc ≤ finalization_hlc, reject as stale.

If write.hlc > finalization_hlc (rare), the write is causally after finalization — it must be treated as a new write in the current epoch and routed according to the committed ring (not allowed to resurrect the old lease). The node must forward the write to the current owner(s) for that key and not accept it locally for the old range.

This rule prevents resurrection: finalization_hlc is the E_safe watermark; anything ≤ it is frozen.

Finalization marker semantics and E_safe watermark
The finalization marker is a Raft-committed log entry that includes:

finalization_marker_id (matches token),

range_id,

finalization_hlc (HLC sampled by the node requesting finalization),

transfer_nonce,

checksum_summary (optional),

new_owner_node_id.

E_safe watermark = finalization_hlc for that range. Once committed:

All nodes must treat any write with hlc ≤ E_safe as immutable and reject attempts to modify that key under the old ownership.

Old owner revokes lease and may GC data for the range.

New owner becomes canonical for writes with hlc > E_safe.

Why HLC on finalization? It gives a single, monotonic, cluster-wide timestamp that bounds causality and prevents late messages from being treated as earlier than the finalization.

Idempotency and write identifiers
client_write_id: client-generated UUID for each logical write. Servers persist a small recent write-id cache per key-range with associated HLC and result. This prevents replayed proxied writes from reapplying after finalization.

per-key sequence: optional for hot keys; sequence numbers are compared against HLC to choose winners deterministically.

Safety proof sketch (invariants)
Token authenticity prevents forged leases.

Lease validity tied to Raft epoch ensures Raft can revoke leases by committing a newer epoch or finalization.

E_safe watermark (finalization_hlc) ensures any write with hlc ≤ E_safe cannot be accepted after finalization.

Idempotent write ids prevent replayed messages from changing state.

Proxying rule ensures serialization during transfer: proxied writes are applied by the lease-holder and carry HLCs that are compared against finalization_hlc.

Together these guarantee: no write that logically precedes or equals the finalization can be applied after finalization, and no delayed proxied write can resurrect the old lease.

This token and lease architecture is bulletproof. Using an HMAC-signed token bound to a specific Raft epoch is brilliant because it decentralizes verification. The io_uring worker threads can validate a token instantly via a fast crypto check without ever needing to query the Raft leader's state machine, keeping the data plane entirely unblocked.

Furthermore, defining the E_safe watermark explicitly as the finalization_hlc solves the resurrection problem elegantly. A delayed packet is no longer an ambiguous threat; it is subjected to a strict mathematical threshold. If the packet's HLC is older than the finalization_hlc, it is provably stale and dropped. If it is newer, it causally belongs to the new epoch and is routed accordingly. The old lease remains dead.

This design achieves Spanner-like consistency without the massive overhead of TrueTime.
