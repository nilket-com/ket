# Aggregated Open Questions (Thematic Grouping)
**Date:** 2026-04-17

This document synthesizes and categorizes the open questions generated by the team (Claude, Codex, Gemini) during the Workstream decomposition phase. It serves as the agenda for the next iteration of planning.

---

## 1. Integration Gate & Production Path Bring-Up
*   **Test Topology:** Should the integration harness run 3 separate OS processes (closer to production, catches signal/config/stderr issues) or 3 in-process nodes with real `quinn::Endpoint` (faster, easier to debug)?
*   **Port Conflicts:** How should we structure the CI environment to ensure real QUIC endpoints don't conflict on port binding when running parallel test suites?
*   **TLS Cert Generation:** Use `rcgen` at test time, or pre-generate and check in fixture certs for tests?
*   **L2 Config Loading:** Should L2 config loading land in this phase even if the gate initially runs without L2 enabled, or should it wait for the Tiering workstream?
*   **Tracing for Bring-up:** What is the minimum tracing/logging install needed to debug bring-up without prematurely designing the full observability stack? Bare `fmt` subscriber, or wire `tracing-subscriber` with env filter + JSON output?

## 2. Rapid Correctness Fixes & Resource Bounding
*   **Concurrency Caps:** What's a reasonable default stream concurrency limit? Should the per-peer concurrency cap be scoped narrowly to inbound QUIC streams first, or wait for a more general admission-control framework?
*   **Dev Secrets:** Is a warning in example config sufficient for deterministic dev secrets, or should the `render_example_config` generation be changed more aggressively?
*   **Scope of Fixes:** Are there other "small but severe" defects (e.g., temporary files from mid-upload crashes) from the assessment that should be moved into this rapid workstream now rather than later?

## 3. Raft Durability Lifecycle & Snapshots
*   **WAL Compaction Strategy:** File rotation (simplest) vs. hole-punch (preserves single file, less disk churn) vs. rewrite (most flexible)? Does `fallocate` interact correctly with `O_DIRECT`?
*   **openraft Integration:** `openraft` has its own `purge_log` and snapshot machinery. Are we fighting the framework by implementing durable purge ourselves, or is this the intended integration point?
*   **Snapshot Trigger Policy:** Who decides when to take a snapshot? The snapshot interval / log-count threshold should be explicit.
*   **Checkpoints:** Should checkpoint emission be tied to snapshot boundaries first, or exist as an independent periodic mechanism?
*   **Snapshot Chunking & Compression:** Should snapshot chunking use a fixed byte size or semantic boundaries? Is large-snapshot chunking a hard requirement for first pilot readiness? Which compression codec (zstd vs lz4)?

## 4. Object Storage Tiering (L2)
*   **ObjectStore Trait Redesign:** Range-GET changes the trait shape. Should we batch Range-GET, streaming put, multipart, and list into a single breaking change early on?
*   **Slab Record Offset Index for Range-GET:** Stored as S3 object metadata, as a sidecar manifest object, or embedded as a header in the slab blob itself?
*   **Pending-Upload Tracking:** How should pending-upload tracking be represented: Raft-managed state, local journal file, or a hybrid?
*   **Orphan GC:** Should Orphan GC run leader-only (safest) or any-node (requires quorum read)?
*   **Multipart Upload:** At what slab size should multipart kick in? Align with `slab_max_bytes`?
*   **Remote Reclaim:** How much remote object reclaim should land in this workstream versus a later retention/archival policy pass?

## 5. Encryption at Rest
*   **Algorithm Choice:** AES-256-GCM vs. XChaCha20-Poly1305? GCM has AES-NI acceleration but strict 96-bit nonce constraints. XChaCha20 has a 192-bit nonce.
XChaCha20-Poly1305
*   **`O_DIRECT` Alignment:** Does the encryption layer sit above or below the `AlignedBuf` page alignment? If above, ciphertext must be padded to page boundaries. If below, alignment logic must account for nonce + tag overhead.
*   **Encryption Granularity:** Per-record (finest-grained, supports per-tenant keys), per-page, or per-slab (simplest, limits tenant isolation within slabs)?
*   **L2 Encryption Implementation:** Should the first implementation use client-side envelope encryption for L2, provider-managed SSE-KMS, or support both from the start?
*   **Key Caching:** How long to cache unwrapped DEKs? Too short = KMS round-trips; Too long = memory exposure risk.
*   **FIPS Interaction:** If FIPS mode is enabled, does `aws-lc-rs` support the chosen cipher?
*   **Migration:** Is a background re-encryption tool for existing plaintext data in scope for this workstream?

## 6. Security, Authorization & Compliance
*   **Authorization Mechanism:** Certificate OID extension vs. separate operator CA vs. token-based authentication?
*   **Authorization Model Scope:** How narrow can the initial control-plane authorization model be while still being credible for a pilot?
*   **Audit Log Design:** NDJSON file is the minimum. Should we support direct syslog/SIEM forwarding from the start? Should records include a hash chain for tamper detection?
*   **FIPS Certification Scope:** Is the goal just "builds with a FIPS-validated crypto module" or full FIPS 140-3 certification of the Wendelon binary?
*   **Rate Limiting Granularity:** Per-IP, per-node-id, or per-connection?

## 7. Observability, Tracing, and Operations
*   **OTLP vs. Jaeger-native:** Support OTLP only and let the collector translate, or support both?
*   **Metrics & Health Endpoints:** Should the health/readiness endpoint require auth? Should metrics and health share the same port? Should secure metrics exposure be solved here directly, or partially in the security workstream?
*   **CLI Design:** Should the CLI be bundled into the main binary (e.g., `wendelon admin cluster-status`) or shipped as a separate standalone binary?
*   **Required CLI Commands:** Which operator CLI commands are required for the first pilot, and which can wait?
*   **Tracing Depth:** How much OTEL/tracing depth is required before pilot readiness versus later operational maturity?

## 8. Fault Injection and Correctness Testing
*   **Simulator Choice:** `madsim` vs. `turmoil` vs. custom? The key blocker is whether `io_uring` and `quinn` usage can be cleanly abstracted for simulation.
*   **Resource Simulation:** Can `io_uring` and S3 `ObjectStore` be swapped for simulated implementations that the fault injector controls?
*   **Coverage Strategy:** Should the first deterministic fault harness use an existing simulator approach, a process-level chaos harness, or both in stages? How many operations in CI vs. nightly?
*   **Linearizability Checker:** Use an existing checker (like Knossos) or build a simple monotonic-counter checker?

## 9. Performance, Scale Hardening, and Resource Control
*   **Durability Guarantees (`fsync` vs `O_DIRECT`):** Is `O_DIRECT` alone sufficient for media durability without explicit `fsync` on PLP NVMe target hardware, or must we implement strict group-commit fsync?
*   **Group Commit Window:** What's the right coalesce interval?
*   **Persistent Index Store:** `redb`, `sled`, periodic checkpoint file, or something else?
*   **Scrubber Repair Automation:** Should the scrubber automatically trigger replica repair when it finds corruption? How much repair automation belongs here versus later tooling?
*   **Memory Budget Enforcement:** Use a global `Arc<AtomicUsize>` or a semaphore-based approach with permits? How broad should the first admission-control layer be?
*   **Buffer Optimizations:** Which whole-buffer paths are pilot blockers versus performance follow-ups?

## 10. Multi-Tenancy & Policy Expansion
*   **Pilot Requirement:** Is multi-tenancy required for the first real pilot, or should this remain explicitly post-pilot?
*   **Namespace Scheme:** Key prefix (simple, but every key gets longer) vs. separate keyspace/slab-per-tenant (cleaner isolation, more complex routing)?
*   **Tenant Identity Propagation:** How does the system know which tenant a request belongs to? Extracted from client cert, request header, or connection identity?
*   **Quota Enforcement Point:** At the data server (admission control) or at the Raft state machine (consensus-level enforcement)?
*   **Tenant Lifecycle Management:** How are tenants created, suspended, and deleted?
*   **KMS Performance Penalty:** How should we model the performance penalty of managing multiple distinct KMS encryption contexts per I/O batch for different tenants?
*   **Per-Tenant Variables:** Can different tenants have different Replication Factors? Should per-tenant L2 routing and per-tenant key isolation land together?
*   **Existing Plan Alignment:** How do these changes align with the existing `plans/ops/multi_tenancy.md` document?
