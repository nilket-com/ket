# ADR 023: L2 Upload Lifecycle (Raft-Authoritative with Non-Authoritative Local Ledger)

## Status
Proposed

## Context
ADR 006 declared that the background Sweeper uploads sealed slabs to L2 but did not specify the durability contract for in-flight uploads. A production tiering path must answer four questions at once: what state persists in Raft (replicated, audited, consensus-bound), what state persists only on the uploading node (provider-owned transient artifacts that have no meaning on any other node), how a restarted node reconciles those two sources, and when the upload switches from single-PUT to multipart. Getting any of the four wrong produces either bloated Raft state (every provider-assigned `UploadId` replicated to every node) or orphaned remote objects across crashes (every failed upload leaves dangling multipart parts that no one cleans).

Forces in play:
- **Raft is the only cluster-wide durability primitive.** The lifecycle of "this slab now lives on L2 and is safe to purge locally" is a cluster-wide decision; it has to be Raft-committed or followers cannot safely evict their copies.
- **Provider-assigned transient state is useless on other nodes.** An S3 `UploadId`, a temp-file path under `/var/lib/wendelon/staging/`, a part-number-to-ETag map — these belong to one node's execution. Replicating them bloats the state machine with data no follower can act on.
- **Node restart is the failure mode the design turns on.** If a node crashes mid-upload, it must know on restart whether the upload made it to `Uploaded` (Raft-committed) or was abandoned (in-flight in the provider). `ListMultipartUploads` is the authoritative-but-slow fallback; the local ledger is the authoritative-for-this-node-and-fast primary.
- **Part size is a tuning knob, not a fixed constant.** Providers floor it (S3: 5 MiB except for the last part); network conditions cap it (a 128 MiB retry over a saturated egress link is pure waste); the chosen size lives in a 8-16 MiB window that every major provider accepts and that retries gracefully.
- **ADR 021 §4's quota enforcement depends on commit-time accounting.** The transition from `Uploaded` to `Committed` is where the `(tenant_id → total_bytes)` Raft counter increments. Getting the transition semantics wrong re-opens the quota race.

Derived from `plans/gap/claude_answers_20260417.md` §4 (pending-upload recovery model, multipart threshold).

## Decision

1. **Lifecycle state machine (Raft-authoritative).** Each slab bound for L2 progresses through a small, totally ordered state set recorded in the Raft state machine. The state is one field on the `tiered_slabs` record keyed by `slab_id`:

   ```
   Pending ──► Uploaded ──► Committed ──► Retired ──► Reclaimed
      │            │
      └──► Aborted ──► Reclaimed
   ```

   - **`Pending`.** A sealed L1 slab has been selected for upload. The state machine records `slab_id`, `tenant_id`, `target_tier` (e.g., `L2:primary`, `L2:archival`), `slab_size_bytes`, `wrapped_slab_dek_ref` (points at the wrapped DEK in the slab footer per ADR 022 §5, not the DEK bytes), `upload_leader_node_id`, `attempt_count`, and `created_hlc`. The slab is still readable from L1; readers prefer the L1 copy.
   - **`Uploaded`.** The object is fully written to the provider. The state machine adds `provider_etag`, `provider_uploaded_hlc`. The L1 copy is still present; readers may prefer either. This state is Raft-committed *after* the provider returns a terminal success (ETag on single-PUT or `CompleteMultipartUpload` response on multipart), never on a best-effort "probably succeeded" signal.
   - **`Committed`.** The authoritative L2 location is now the canonical location for this slab. Tenant quota accounting (ADR 021 §4) increments in the *same Raft commit* that transitions the slab to `Committed`. Entering `Committed` is a second Raft commit after the provider-side success that produced `Uploaded`, because it is conditional on orthogonal signals (migration sweeper progress, operator-configurable grace period, archival-tier delay-before-purge policy) that do not belong in the upload path itself. **After `Committed`, each replica independently may purge its L1 copy** when its own NVMe pressure warrants; purge is a node-local decision, not a Raft-replicated transition. Per-replica L1 presence is tracked in the node's own redb index (ADR 017) and optionally advertised via gossip for reader-routing hints (reader prefers an L1-holding replica when present), but the cluster-wide authoritative state for a `Committed` slab is "bytes are durable on L2 and tenant quota is accounted"; whether any given replica still holds an L1 copy is a local optimization that does not change the slab's authoritative status.
   - **`Retired`.** Policy has decided this slab is no longer needed. The state machine adds `retired_hlc` and `retire_reason` ∈ {`compaction_retired`, `retention_expired`, `migration_old_copy`, `tenant_deleted`}. The L2 object is still present at the provider; ADR 024's reclaim sweeper picks up `Retired` records and deletes the remote bytes after the reason-specific grace period. Moving to `Retired` is Raft-committed by the leader; it is the authoritative marker that ADR 024 Tracks B and C join on.
   - **`Reclaimed`.** The L2 object (or, on the `Aborted` branch, the orphaned multipart residue) has been deleted from the provider. `Reclaimed` is a terminal state and the record is eligible for state-machine GC after the next snapshot boundary. Tenant quota accounting decrements (ADR 021 §4) in the same Raft commit that records `Retired → Reclaimed` for slabs that had previously been counted (i.e., slabs that reached `Committed`). `Aborted → Reclaimed` does not move the quota (the slab never reached `Committed` and was never counted).
   - **`Aborted`.** The upload terminated without success, *or* the reclaim sweeper synthesized a record to represent an unreferenced provider-side artifact so that its cleanup is observable as a state transition. Raft records `aborted_hlc` and `abort_reason` ∈ {`provider_error_terminal`, `retry_exhausted`, `operator_abort`, `leader_transition`, `orphan_detected`}.
     - `provider_error_terminal`, `retry_exhausted`, `operator_abort`, `leader_transition` are produced by the uploader as terminal outcomes of an active `Pending` or `Uploaded` record (`Pending → Aborted` or `Uploaded → Aborted`).
     - `orphan_detected` is produced *only* by ADR 024 Track D's full-bucket orphan GC, and *only* as a synthetic-record **insertion** directly into `Aborted` — never as a transition from another state — for an object key that exists at the provider but has no `tiered_slabs` record. The synthetic record is advanced to `Reclaimed` in the same Raft commit batch that records the delete. No other caller may insert an `Aborted(orphan_detected)` record; no other `abort_reason` may be used for the insert-directly-into-`Aborted` path.

     ADR 024 Track A sweeps partial remote state for uploader-produced `Aborted` records (via `ObjectStore::abort_multipart` and `list_multipart_uploads`); when that sweep succeeds the record advances to `Reclaimed`. The synthetic `Aborted(orphan_detected)` path is not reclaimed by Track A; ADR 024 Track D deletes the orphaned object and advances that synthetic record to `Reclaimed` in the same reclaim batch. L1 retains the slab indefinitely until a subsequent upload attempt creates a new `Pending` record.

   Every state transition is a distinct Raft log entry. Every transition emits an audit event (ADR 025 planned). The state machine rejects transitions that violate the ordering (e.g., `Pending → Committed` without passing `Uploaded`, or `Committed → Aborted`) to catch implementation bugs as hard failures rather than silent skips. Valid transitions are exactly: `Pending → {Uploaded, Aborted}`, `Uploaded → {Committed, Aborted}`, `Committed → Retired`, `Retired → Reclaimed`, `Aborted → Reclaimed`. **Direct insertion** of a record is permitted in exactly two states: `Pending` (the normal uploader-driven entry point) and `Aborted(orphan_detected)` (the ADR 024 Track D synthetic-record path, restricted to the reclaim sweeper's narrowed proposal surface). No other direct insertions and no other transitions are accepted.

2. **Local execution ledger (non-authoritative, node-local).** Each uploading node maintains a durable, node-local ledger that records the *execution-local* state that has no meaning on any other node. The ledger is a redb table (ADR 017) keyed by `slab_id`; rows are upserted synchronously with every provider-side mutation and pruned when the Raft state reaches a terminal state:

   ```
   slab_id (primary key)
   upload_id          (provider-assigned, bytes)
   temp_file_path     (absolute path under the staging directory; empty once the slab is persisted as a single file)
   parts              (ordered list of {part_number: u32, size_bytes: u64, etag: bytes, uploaded_hlc: u64})
   last_attempt_hlc   (u64; used for retry backoff)
   retry_count        (u32)
   last_error_kind    (enum; transport, provider_5xx, provider_4xx, checksum_mismatch, timeout, canceled)
   ```

   The ledger is durable (fsync-on-write) because its purpose is to survive the same crashes that make it necessary. It is intentionally **not** replicated: if a node's disk is replaced, the ledger vanishes and recovery falls back to the provider-side listing path (decision §4). Ledger writes happen before the corresponding provider mutation (to record "we are about to call `UploadPart N`") and are idempotently updated after (to record the ETag the provider returned).

3. **Multipart trigger and part sizing.**
   - **Trigger.** Multipart kicks in for any slab whose size is at or above `slab_max_bytes`. Because ADR 020 §2's ceiling is 32 GiB and real slabs run 64 MiB to a few GiB, every slab in practice goes multipart. Smaller slabs (produced by special-case low-volume tenants, or by E_safe compaction into a stub slab) use single-PUT; the branch is a one-line size check in the uploader. Provider-default trigger thresholds (S3's "multipart recommended above 100 MB") are advisory noise — the slab sizing is the authoritative configuration, not a provider default.
   - **Part size.** 16 MiB default, tunable in `[provider_floor, 64 MiB]`. S3's floor is 5 MiB for all parts except the last. A failed 128 MiB retry over a congested egress path wastes a minute of bandwidth; 16 MiB retries complete in single-digit seconds on a saturated but healthy link. The clamp at 64 MiB is a defense against operator misconfiguration — a 256 MiB part size is not a meaningful optimization on any realistic network.
   - **Part numbering.** Parts are numbered starting at 1 (S3 requirement). The uploader issues parts in ascending order but does not require sequential completion — parallel in-flight parts are bounded by the admission-control memory budget (per ADR 021's data-path admission layer and `plans/ops/resource_control.md`).

4. **Recovery protocol.** On node restart, each node with an unfinished upload role executes the following sequence per `Pending` slab where this node is `upload_leader_node_id`. All provider calls below go through the `ObjectStore` trait defined in ADR 022 §8:

   1. **Consult the Raft state.** If the state machine shows `Committed`, `Retired`, `Reclaimed`, or `Aborted`, no further provider-side action is needed; the local ledger entry (if any) is pruned. If the state shows `Uploaded`, the slab was already durably at the provider before the crash; the node proceeds to the `Uploaded → Committed` gate (which is evaluated by the leader at its own cadence).
   2. **Consult the local ledger.** If the ledger shows an `upload_id`, the node calls `ObjectStore::list_parts(key, upload_id, ...)` to reconcile the ledger's view with the provider's view. Discrepancies (parts recorded locally but missing at the provider) are treated as retryable; the node re-hydrates a handle via `ObjectStore::resume_multipart(key, upload_id)` and re-uploads the missing parts. Extra parts at the provider with no ledger entry are treated as pre-crash successes and adopted into the ledger. If all parts are present, the node calls `MultipartUpload::complete` on the resumed handle with the accepted part list and, on success, proposes the `Pending → Uploaded` Raft transition.
   3. **Fall back to `list_multipart_uploads`.** If the local ledger is missing (disk replaced, node rebuilt, staging directory wiped) but the Raft state still shows `Pending`, the node issues `ObjectStore::list_multipart_uploads(prefix = tenant/{tenant_id}/slab/{slab_id}, ...)` — a deterministic prefix per §5. Any matching `upload_id` is adopted into a fresh ledger entry and the reconciliation in step 2 proceeds. If no matching upload exists, the node treats the slab as "upload never started or was abandoned server-side" and restarts the upload with a fresh `put_multipart` call.
   4. **Abort-on-retry-exhaustion.** If retry-count exceeds the configured ceiling (default 10, tunable) or if the provider returns a terminal 4xx, the node proposes `Pending → Aborted` with the error reason. The remote multipart (if any) is aborted by calling `ObjectStore::abort_multipart(key, upload_id)` or, equivalently, `MultipartUpload::abort` on a live handle; any residual parts not reached by this abort path are swept by ADR 024 Track A, which then advances the record to `Reclaimed`.

5. **Object-key naming is deterministic.** The L2 object key is `tenant/{tenant_id_hex}/slab/{slab_id_hex}.wnd`. This gives:
   - Deterministic lookup from the Raft state (no key mapping table).
   - A clean tenant-prefixed listing path so ADR 024's paged LIST-join orphan-GC can scope its work per tenant and short-circuit on deleted tenants.
   - A filterable prefix for `ListMultipartUploads` during recovery (decision §4 step 3).
   - A natural per-tenant bucket-routing pivot if a future per-tenant L2 bucket landing (ADR 021 §8 phase 2) is exercised.

   Naming is **not** negotiable per-tenant: a tenant cannot choose its own key format. Per-tenant bucket routing is a post-pilot capability (ADR 021 §8); it changes the bucket, not the key within it.

6. **Leader-scoped upload authority.** The node that proposes the `Pending` state is the upload leader for that slab. Other nodes never attempt to upload the same `slab_id` concurrently. If the upload leader is deposed (node failure, operator transfer), the new leader observes the stale `Pending` record, evaluates its own ledger (likely empty — this is a different node), and either re-drives the upload (ledger-based resume if some replica persisted the ledger through a node handoff path — not supported in pilot) or, much more commonly, aborts the stale `Pending` and issues a fresh `Pending` under its own `upload_leader_node_id`. The fresh upload uses a new `UploadId`; the orphaned provider-side multipart is swept by ADR 024.

7. **Per-provider abstraction is part of the `ObjectStore` trait from ADR 022.** This ADR does not name AWS S3 versus GCS versus Azure Blob versus a future vendor. The `MultipartUpload` trait (ADR 022 decision §8) is the surface; provider-specific behaviors (GCS resumable uploads map onto the same lifecycle but with different wire-level semantics) live behind the trait. The test path uses the mocked `ObjectStore` (ADR 028) and `rustfs` (ADR 014); integration tests against real providers run in the nightly tier.

## Rationale

- **Two sources of truth, one with higher authority, is the only answer that survives.** Pure-Raft replicates provider `UploadId`s that are meaningless on followers and bloats the state machine. Pure-local allows a restart to acknowledge an upload that Raft never committed — creating the possibility of L1 purge on a slab Raft doesn't believe is safe. The hybrid — Raft for lifecycle, local ledger for execution, provider-listing as fallback — is the only shape that answers every restart scenario.
- **Separating `Uploaded` from `Committed` is load-bearing.** The transition from "provider has the bytes" to "the cluster considers L2 canonical" is conditional on orthogonal policy (grace period, archival delay, cross-region replication confirmation for tiers that support it). Folding them into one transition would force policy decisions into the upload path, or force every policy-gated feature to evolve through upload-code changes.
- **Quota accounting at `Committed` avoids double-counting.** A slab that reaches `Uploaded` but later aborts (e.g., a cross-region replication failure in a multi-tier policy) never increments the tenant's quota. Accounting on `Uploaded` would require a decrement on the abort path and would be vulnerable to the decrement being lost across a leader transition.
- **`ListMultipartUploads` fallback is a correctness backstop, not a performance path.** The common-case recovery uses the local ledger and finishes in two provider RPCs (`ListParts`, then `CompleteMultipartUpload`). The `ListMultipartUploads` fallback fires only on disk-loss, is bounded by the provider's pagination, and trades N additional round-trips for correctness under disk-loss scenarios. Operators who rebuild nodes without preserving the staging volume accept the slower recovery as the cost of that operational choice.
- **Multipart-for-everything simplifies the hot path.** The branch between single-PUT and multipart exists but runs for the rare small-slab case. The uploader's steady-state is one code path with one set of failure modes. Branching pervasively to optimize the small-slab case is negative ROI.
- **Part size 8-16 MiB is the empirical sweet spot.** AWS, GCS, and Azure all accept parts in this range; all three have retry-cost curves where 8-16 MiB is near-optimal. The 64 MiB ceiling is a defense against operator over-tuning; the provider floor (5 MiB on S3) is the hard lower bound.
- **Deterministic key naming is worth more than per-tenant flexibility.** A tenant's ability to name its own objects in the shared bucket would buy convenience at the cost of: (a) ADR 024's list-join GC becomes per-tenant-path-aware rather than prefix-scannable; (b) `ListMultipartUploads` recovery becomes per-tenant-naming-aware; (c) the Raft state machine has to store the naming policy. Uniform naming is structurally simpler and loses nothing that per-tenant bucket routing (ADR 021 §8 phase 2) does not already cover.

## Consequences (The "Negatives")

- **Three Raft commits per slab in the common path (`Pending`, `Uploaded`, `Committed`), plus two more at end-of-life (`Retired`, `Reclaimed`) for slabs that reach reclamation.** At high L2 write rates this adds measurable state-machine churn. Mitigated by: (a) the commits are tiny (slab_id-scoped records, not payload), (b) they batch via the consensus group-commit window, (c) the `Pending → Uploaded` span is the only long-duration state and does not block any other tenant's upload, (d) ADR 024 decision §5 batches `Retired → Reclaimed` transitions into grouped `reclamation_event` commits so the reclaim phase does not produce one Raft commit per slab.
- **Local ledger loss forces `ListMultipartUploads`.** An operator who wipes a node's staging volume without also aborting the node's in-flight multiparts pays a full-bucket `ListMultipartUploads` at restart. On a large bucket this is minutes of recovery work. Mitigated by: staging volume guidance in the operator runbook, and by `ListMultipartUploads` being paginated and providing a `CreatedAfter` filter on most providers.
- **Cross-node upload resume is unsupported in pilot.** If node A crashes mid-upload and node B takes leadership, node B does not inherit node A's provider-side multipart state. Node B aborts node A's `Pending` and starts fresh. Accepted because the alternative (replicating the local ledger, or using a multi-writer upload coordination protocol) adds substantially more complexity than the rare cross-node-upload-resume scenario is worth.
- **Deterministic key naming exposes `tenant_id` in the object key.** An attacker with bucket LIST permission can infer tenant cardinality and activity. Mitigated by: (a) the bucket is not publicly listable by design, (b) provider IAM policy is the first gate, (c) tenant activity is already exposed via the audit stream to anyone with audit access.
- **Retry-count ceiling (default 10) can give up prematurely on a flaky provider.** A tenant experiencing a sustained provider-side outage may see its slabs go `Aborted` after 10 retries instead of continuing to retry indefinitely. Accepted because: (a) 10 retries with exponential backoff already covers ~20 minutes of outage, (b) operator intervention is appropriate for sustained outages, (c) the ceiling is tunable, (d) indefinite retry masks real incidents.
- **The `Uploaded → Committed` transition introduces a gap window where both L1 and L2 hold the slab.** Accepted as the structural cost of making the transition policy-driven. The gap is bounded by the configured grace period (default 5 minutes, tunable) and by L1 free-space pressure; L1 purge is a per-replica decision taken after `Committed`, not a replicated lifecycle transition, precisely so each node can trade L1 retention against its own NVMe pressure without forcing a cluster-wide step.
- **Rejected alternatives explicitly:**
  - *Pure-Raft lifecycle (including UploadId, temp-file path, parts)* — rejected for bloating replicated state with provider artifacts and replicating data that has no meaning off the uploading node.
  - *Pure-local lifecycle (Raft only observes terminal outcomes)* — rejected because followers cannot safely purge their L1 copies without a Raft-committed `Committed` state, and because there is no authoritative replicated audit trail for upload lifecycle.
  - *Single fixed part size (e.g., 128 MiB)* — rejected for retry-cost pathology on congested networks.
  - *Unified `Uploaded == Committed` state* — rejected for forcing grace-period and archival-policy decisions into the upload code path.
  - *Cross-node upload resume via replicated ledger* — rejected for complexity vs frequency; deferred as a post-pilot feature if measured demand justifies it.
  - *Per-tenant object key naming policy* — rejected for costs to orphan-GC, recovery, and Raft state; per-tenant bucket routing (ADR 021 §8) is the right abstraction for per-tenant physical isolation.

## Open Questions

All items below must be closed before this ADR moves from Proposed to Accepted.

- **`Uploaded → Committed` gate policy.** The conditions that gate the promotion (grace period duration, minimum replica count confirming local ledger presence, archival-tier-specific delay) are specified qualitatively but not numerically. The default 5-minute grace is a placeholder. *Resolves via:* a policy design note that enumerates the gate inputs and their default values, cross-referencing `plans/ops/storage_tiering.md` §2.
- **Part-size tuning for GCS and Azure.** The 8-16 MiB window is validated against AWS S3. GCS (resumable uploads) and Azure Blob (block blobs) have different optimal windows. *Resolves via:* a provider-specific benchmark during Wave 4 implementation; the ADR commits to a per-provider default overridable via config.
- **Ledger retention after terminal states.** How long the local ledger retains rows for `Committed` / `Retired` / `Reclaimed` / `Aborted` slabs. Long retention helps forensic debugging; short retention bounds redb growth. *Resolves via:* a configurable retention window (default 7 days); resolved at implementation time unless measurement reveals a correctness constraint.
- **Concurrency ceiling on in-flight uploads.** The number of concurrent multipart uploads per node and the number of in-flight parts per upload are admission-control tuning questions that depend on the node's memory budget (ADR 021 §3 data-path admission layer) and on the provider's per-account concurrency limits. *Resolves via:* implementation-time benchmark under the admission-control framework; the ADR commits to the ceiling being admission-governed, not to specific values.
