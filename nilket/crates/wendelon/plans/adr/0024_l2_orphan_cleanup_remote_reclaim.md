# ADR 024: L2 Orphan Cleanup and Remote Reclaim

## Status
Proposed

## Context
ADR 006 declared that the Sweeper is responsible for Tiering and Migration but did not address how the cluster keeps its L2 objects in sync with its authoritative view of which slabs should exist. Four separate failure modes leave remote state that the cluster does not (or no longer) believe in:

1. **Aborted multipart uploads** (ADR 023) leave provider-side parts that count against the tenant's storage cost but are not referenced by any slab.
2. **Migration cleanup** after an epoch transition (ADR 006) leaves slabs whose logical ownership has moved to a new node, but whose old copy still exists at the provider until reclaimed.
3. **Retention and tombstone expiry** — E_safe compaction (ADR 002 epoch framing + `plans/ops/storage_tiering.md` §4 Policy 4) produces dead slabs that are replaced by fresh compacted output. The old slab must be deleted from L2, not merely from L1.
4. **Retirement of a `tiered_slabs` record without the object being deleted** — e.g., a slab reaches `Committed`, replicas purge their L1 copies locally as NVMe pressure warrants, and later compaction or retention transitions the record to `Retired(retire_reason)`; the provider-side bytes must then follow.

Without a reconciler, remote state diverges from Raft state monotonically: every failure mode adds objects that no one deletes, and operators discover the problem via the bill. Silent cost-growth is the worst class of bug a tiered storage system can have.

Forces in play:
- **The leader has the freshest state.** Followers can see a stale view of the `tiered_slabs` table across a partition. Destructive operations executed on stale state irreversibly delete live data.
- **LIST is paginated and expensive on large buckets.** A bucket with 10M slabs requires ~10k LIST calls (S3's 1000-per-page default). Full-bucket scans cannot be the steady-state reclamation path; they are the safety net for the cases that incremental signals miss.
- **Delete is irreversible.** Accidental deletion of a live slab that Raft still references is a durability violation. The reclaimer has to be structurally incapable of deleting a slab that any `tiered_slabs` record references — not merely unlikely to.
- **Rate limits are not optional.** A provider rate-limits DELETE (S3: 3500 DELETEs/second per prefix); exceeding the limit produces 503s and cascading retry storms. A naive delete-all-orphans sweep can take a well-loaded provider into throttling within seconds.
- **Archival tiers have different delete semantics.** Glacier-class storage has minimum-storage-duration charges that make early deletion a cost anti-pattern. Archival-tier reclamation policy is a different problem from hot-tier reclamation.

## Decision

1. **Leader-only reclaim authority.** Only the Raft leader evaluates reclamation candidates and issues deletes. Followers never issue DELETE or `AbortMultipartUpload` against the provider. The leader election mechanism (ADR 007 / `openraft`) is the gate: a node that loses leadership stops reclaiming mid-batch, and the new leader picks up the reclaim scan from scratch on its own cadence. Reclaim state is not checkpointed across leaders — the scan is idempotent and restartable, which is cheaper than a distributed cursor.

2. **Four-track reclaim, one sweeper.** A single leader-resident sweeper task runs all four tracks; each track has its own cadence and its own state-machine join. The tracks share a common rate-limiting budget (decision §4) so that a burst in one track does not crowd out the others. ADR 023 defines the authoritative lifecycle; this sweeper drives the terminal transitions (`Retired → Reclaimed` and `Aborted → Reclaimed`) and issues the provider-side deletes that accompany them. All provider calls go through the `ObjectStore` trait from ADR 022 §8.

   - **Track A — Orphan multipart abort.** Periodic (default every 6 hours). Calls `ObjectStore::list_multipart_uploads(prefix = tenant/)` paged, filters for `initiated_at < now - grace`, joins against the `tiered_slabs` state machine. Any `(key, upload_id)` not referenced by a `Pending` or `Uploaded` record — or referenced by an uploader-produced record already in `Aborted` — is aborted via `ObjectStore::abort_multipart(key, upload_id)`. Grace defaults to 1 hour to avoid racing ADR 023 §4 recovery; operator-tunable. For records already in `Aborted` whose provider-side abort has now completed, Track A proposes `Aborted → Reclaimed`. Track A does **not** synthesize `Aborted(orphan_detected)`; that reason is reserved to Track D's synthetic-record insertion for whole-object orphans, not multipart residue.
   - **Track B — Migration cleanup.** Event-driven. Fires on `epoch_committed` events (ADR 002) and joins the new epoch's routing table against `tiered_slabs`. For each slab whose authoritative owner has moved: once the new owner's copy reaches `Committed` and the migration lease expires (default 48 hours), the leader proposes `Committed → Retired(reason=migration_old_copy)` on the *old* copy's `tiered_slabs` record. Track B then deletes the L2 object for slabs it has marked `Retired(migration_old_copy)` after the reason-specific grace (default 0 hours beyond the lease — the lease already serves as the cooling window), and advances the record to `Reclaimed`. The old slab's L1 copies are purged by each replica's local sweeper on the same `Retired` signal.
   - **Track C — Retention / tombstone reclamation.** Event-driven on E_safe advance and on tenant-lifecycle transitions (ADR 021 §6: `deleted` tenant → destroy KEK → delete every slab belonging to that tenant). The leader proposes `Committed → Retired(reason)` on each reclamation candidate — `reason=retention_expired` for slabs whose `max_hlc < global_E_safe_floor` and that have been superseded by compaction output; `reason=compaction_retired` for slabs explicitly retired by Policy 4 E_safe compaction (`plans/ops/storage_tiering.md` §4); `reason=tenant_deleted` for slabs of a deleted tenant. Track C then deletes the L2 object for slabs marked `Retired(retention_expired)` or `Retired(compaction_retired)` after a configurable grace (default 24 hours from the `Retired` timestamp) and advances to `Reclaimed`. Tenant-delete reclamation is unconditional once the `deleted` state is Raft-committed; the KEK is already destroyed so the bytes are unreadable, and the reclaim is a cost and inventory hygiene step, not a correctness one — the grace for `Retired(tenant_deleted)` defaults to 0 hours.
   - **Track D — Full-bucket orphan GC.** Periodic (default every 72 hours, operator-tunable). Paged `ObjectStore::list(prefix = "tenant/")` join against the full `tiered_slabs` state machine; any object key present at the provider but absent from the state machine (i.e., no `tiered_slabs` record of any state) is a candidate orphan. Track D catches the leak cases the lifecycle does not model — e.g., a crashed `put_multipart` that somehow committed to a single object at the provider after its `tiered_slabs` record was already advanced to `Aborted`, or an object from a previous Wendelon version that predates the current schema. Candidates are not deleted on first observation; they are placed on a "suspected orphan" list (non-authoritative, sweeper-local) with a timestamp. On a subsequent pass (default 24 hours later), if the object is still present and still absent from the state machine, the sweeper proposes a synthetic `tiered_slabs` record in state `Aborted(abort_reason=orphan_detected)` and then advances it to `Reclaimed` in the same commit batch as the delete. The synthetic-record step keeps Track D's audit trail uniform with the other tracks: every delete is observable as a state transition in the replicated log, not as a side-effect that only the sweeper remembers.

3. **Delete is gated by a freshness check against the leader's own committed state.** Immediately before issuing a DELETE or `abort_multipart`, the sweeper re-reads the `tiered_slabs` record for the target `slab_id` at the leader's current committed log index. The delete proceeds only if the record is in one of the reclaim-eligible states: `Aborted` (for Track A multipart cleanup) or `Retired(reason)` (for Tracks B and C). Any other state — including `Pending`, `Uploaded`, `Committed` — cancels the delete and drops the candidate from the batch. Track D's synthetic-record step runs the same recheck after proposing the synthetic `Aborted`. This is not a distributed check — the leader reads its own state — but it bounds the window between "this slab is an orphan" and "we delete its bytes" to the duration of one Raft round-trip worst-case. Slabs added to `tiered_slabs` after the sweeper's scan but before its delete are protected by this recheck.

4. **Per-tenant and per-prefix rate budgets, shared across tracks.** The sweeper uses a token-bucket rate limiter with three levels:

   - **Global bucket.** Default 500 DELETEs/second across all tenants, all tracks. Defense against a provider-wide throttle that would cascade into retry storms.
   - **Per-tenant bucket.** Default 50 DELETEs/second per tenant, carved from the global. A tenant in the middle of deletion cannot monopolize the global budget.
   - **Per-prefix bucket.** Default 100 DELETEs/second per top-level key prefix (the `tenant/{id}/slab/` prefix from ADR 023 §5). This aligns with S3's per-prefix throttle and avoids triggering provider-side 503s by local design rather than reactive backoff.

   All three are operator-tunable. A DELETE blocked by any of the three waits; the sweeper is a background task with no latency budget of its own. `AbortMultipartUpload` consumes budget from the same buckets.

5. **Deletions are logged as Raft-committed state transitions (`Retired → Reclaimed` or `Aborted → Reclaimed`) and audited (ADR 025 planned).** Each batch of reclaimed objects produces one `reclamation_event` Raft commit that records the slab IDs, the reason codes (drawn from the ADR 023 `retire_reason` or `abort_reason` values: one of `{migration_old_copy, retention_expired, compaction_retired, tenant_deleted, orphan_detected, provider_error_terminal, retry_exhausted, operator_abort, leader_transition}`), and the reclaiming leader's node_id. The same commit advances the affected `tiered_slabs` records to `Reclaimed` and decrements tenant quota counters (ADR 021 §4) for any slabs that had previously been counted at `Committed`. The reclamation event is the authoritative "we deleted this" record; readers of the audit stream see one uniform entry per batch. `Reclaimed` records are eligible for state-machine GC after the next snapshot boundary — the leader schedules their removal from the `tiered_slabs` table at that point so the state machine does not accumulate terminal rows indefinitely.

6. **Archival-tier reclamation is explicitly deferred.** Glacier-class storage, cross-region replication reclamation, and lifecycle-policy-driven retention at the provider level are out of scope for pilot. The sweeper's archival behavior is "decline to delete"; an archival slab reaches the end of its E_safe life and the state machine records it as `retention_expired` but the remote DELETE is not issued. A follow-up ADR or implementation note (`plans/ops/archival_retention.md`, to be authored post-pilot) covers the archival lifecycle including minimum-storage-duration economics and cross-region replica coordination.

7. **Safety invariants enforced by construction.**
   - The sweeper's delete path is implemented as one function whose inputs are `(slab_id, reason_code, leader_committed_index)`; that function re-reads the `tiered_slabs` record at the given committed index and returns `Err(NotReclaimable)` unless the record is in `Aborted` or `Retired(reason)`. The function is the only call site that is permitted to invoke `ObjectStore::delete` in the tiering subsystem. Direct `ObjectStore::delete` calls from other modules are rejected by the trait-visibility boundary (the tiering module re-exports a narrowed `ReclaimingObjectStore` façade).
   - `ObjectStore::abort_multipart` is similarly routed through a single function that re-checks the `upload_id` against the `tiered_slabs` state (state must be `Aborted`, or the `(key, upload_id)` must be unreferenced by any record for Track A's orphan-multipart case) before aborting.
   - A reclamation event can only be Raft-committed by the leader; non-leader sweeper code is structurally incapable of producing one. Attempted proposals from a non-leader fail at the consensus layer.
   - Unit tests assert that removing any of the safety checks causes the integration test suite (ADR 028 deterministic harness) to fail with at least one live-slab-deleted scenario.

## Rationale

- **Leader-only authority is the minimum viable serialization.** Destructive operations need the freshest possible view of the truth. The alternatives (follower-side deletes with quorum checks; eventual-consistency reclaim with vector-clock reconciliation) trade real complexity for marginal throughput — and they never hit the throughput ceiling that matters, which is the provider's per-prefix rate, not the cluster's ability to generate delete candidates.
- **Four tracks reflect four distinct inputs and cadences.** Conflating them into one "periodic orphan GC" loses the event-driven fast paths (tenant deletion, epoch transition) and makes the full-bucket LIST the workhorse, which scales badly. Separating them keeps the expensive scan rare and the common cases cheap.
- **Delete-on-recheck, not delete-on-scan, is the cheap correctness win.** The scan can be seconds to minutes behind the leader's current state; in that window the state machine can admit a new slab whose object was just created at the provider. The recheck costs one local state-machine read per delete, which is trivial, and it collapses the staleness window to the leader's own commit cadence.
- **Three-level rate budget matches the three throttle dimensions operators actually see.** A global cap stops retry storms during provider-wide degradation; a per-tenant cap stops one tenant's deletion from starving another's; a per-prefix cap aligns with the provider's own throttle model so the sweeper fails below the provider's throttle rather than above it. Conflating the three into one cap forces the operator to choose between safety (low cap, slow reclamation) and throughput (high cap, occasional throttle).
- **Full-bucket LIST at 72-hour cadence is the cost/coverage balance.** Orphan-GC catches failure modes that the incremental tracks miss (provider-side duplications, incomplete aborts, lost Raft commits during leader transitions). Running it continuously wastes LIST calls against the provider; running it monthly leaves orphans on the bill for a month. 72 hours is the measured operational sweet spot for bucket-scale fleets.
- **The delay-then-delete pattern for orphan-GC is defense-in-depth.** A single pass that deletes on first-observation-of-absence is vulnerable to a brief window where the state machine is in an inconsistent state (e.g., during Raft log compaction). A two-pass pattern with a 24-hour pause between passes costs 24 hours of extra storage for real orphans but never deletes a live slab because of a transient state-machine read anomaly.
- **Archival deferral matches the economic shape of archival storage.** Glacier has minimum-storage-duration charges (90 days for Glacier Flexible, 180 days for Glacier Deep Archive) that mean "delete because E_safe advanced" is a cost anti-pattern within the minimum window. The right behavior — "delete only after the minimum-storage-duration has also elapsed" — is enough additional policy surface that it warrants its own ADR rather than being a footnote here.
- **Single-function-delete is a correctness-by-construction win.** The alternative (rely on every caller to check before deleting) is exactly the shape in which a future refactor forgets the check. Centralizing it makes the check impossible to skip.

## Consequences (The "Negatives")

- **Leader death mid-scan wastes the in-progress scan.** A 10k-page LIST that dies halfway restarts from zero under the next leader. Mitigated by: (a) the sweeper running at a cadence where occasional full restarts are a small fraction of provider cost, (b) the leader ordinarily outliving a scan easily.
- **72-hour orphan-GC cadence means orphans live up to 96 hours (72-hour cadence + 24-hour observation delay) before deletion.** For a cluster generating orphans at a meaningful rate this is real storage cost. Mitigated by the three incremental tracks (A, B, C) handling the common orphan sources promptly; Track D exists to catch the cases the incremental tracks miss, and those are by definition rarer.
- **Rate limits can queue deletes indefinitely in a deletion-heavy period.** A tenant-delete operation on a tenant with 10M slabs at 50 DELETEs/second takes ~55 hours. Accepted because: (a) tenant-delete is not a latency-sensitive operation, (b) higher rates produce provider-side throttles that slow deletion overall, (c) operators needing faster bulk-delete can raise the per-tenant rate knob temporarily.
- **Archival-tier deferral means archival slabs accumulate on the bill until the archival ADR lands.** Real cost during the gap. Accepted as the structural cost of not shipping archival-lifecycle policy in pilot; operator guidance is "do not enable archival tiering until the archival-retention ADR ships," and the config schema will emit a warning if archival tiering is configured.
- **The `ReclaimingObjectStore` façade adds a module boundary.** A single wrapping trait to ensure delete-path centralization. Small real cost in module graph complexity; paid in correctness.
- **The four-hour grace on orphan-GC catches most ADR 023 recoveries but not all.** A node that takes more than an hour to restart and resume its multipart uploads will see its uploads aborted by the sweeper. Mitigated by the grace being operator-tunable and by nodes that slow to multi-hour restart already being incident-worthy.
- **Full-bucket LIST is O(bucket_size).** A multi-petabyte bucket with sparse per-tenant activity still pays the full bucket cost every 72 hours. Mitigated by: `list` pagination with per-tenant prefixes, so the sweeper can parallelize across tenants and skip tenants whose state-machine entries match the listing exactly.
- **Rejected alternatives explicitly:**
  - *Any-node delete authority with quorum check* — rejected for the complexity cost of distributed quorum reads vs the simplicity cost of leader-only dispatch, and for the absence of any throughput benefit (provider throttle is the bottleneck, not leader CPU).
  - *Delete-on-scan without recheck* — rejected for the state-staleness window that permits live-slab deletion.
  - *One periodic full-bucket GC as the only reclamation path* — rejected for its inability to respond to tenant-delete, epoch-change, and aborted-multipart events at an operationally responsive cadence.
  - *Eventual-consistency reclaim with vector clocks across leader transitions* — rejected for complexity vs the simplicity of "the leader is the authority; a leader transition restarts the scan."
  - *Archival tiering in pilot* — rejected for minimum-storage-duration economics that require policy surface not yet designed.
  - *Unbounded delete concurrency with reactive backoff* — rejected for the retry-storm pattern it produces under provider throttle.

## Open Questions

All items below must be closed before this ADR moves from Proposed to Accepted.

- **Orphan-GC cadence on very large buckets.** 72 hours is the default; at 10^8 objects a full scan may take longer than 72 hours. *Resolves via:* a benchmark against a provisioned bucket at 10^6 and 10^7 slab counts measuring LIST throughput and join cost; the default becomes bucket-size-aware (e.g., 72 hours up to 10^7 slabs, adaptive thereafter).
- **Concurrent sweeper on a bucket shared across clusters.** If two Wendelon clusters share a bucket (not the default, but not impossible), each cluster's sweeper could observe the other's live slabs as orphans. *Resolves via:* either an ADR-level decision to forbid bucket sharing (with a detection mechanism at config-load time) or a key-prefix convention per cluster. Pilot default will be forbid-and-detect.
- **Provider-side lifecycle policy interaction.** Operators may configure provider-side lifecycle rules (S3 Lifecycle, GCS Object Lifecycle). The sweeper should not conflict; e.g., a provider-side expiry that deletes an object that the state machine still references creates a durability loss. *Resolves via:* a compatibility check at config-load time — if the bucket has an active lifecycle policy targeting the `tenant/` prefix, the daemon refuses to start unless the operator acknowledges with a config flag.
- **Reclamation-event Raft churn at high delete rates.** One `reclamation_event` per batch implies hundreds of Raft commits per hour during tenant-delete or epoch-cleanup bursts. *Resolves via:* a measurement under realistic delete load; if the churn is material, the event is batched larger (up to one per hour) with a bounded fallback to per-batch on smaller deletion counts.
