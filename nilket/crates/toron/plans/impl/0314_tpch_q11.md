# ADR 314 — Implementation plan: tpch.q11 reachability

Pairs with `plans/adr/0314_tpch_q11.md`. Harness-only (`toron-tpch`); no `crates/toron` engine change in this cut.
Verify-first — likely a split (dev green / strict Decimal×Int wall).

## Phase 0 — verify-first probe (measure the split)
Wire the minimum and **measure both modes**:
```
scripts/cargo-cgroup run -p toron-tpch -- run --query q11 --mode dev    --sf 0.01 --allow-blocked
scripts/cargo-cgroup run -p toron-tpch -- run --query q11 --mode strict --sf 0.01 --allow-blocked
```
Expected: strict `blocked(unsupported_decimal_arithmetic@bind)` on `ps_supplycost * ps_availqty` (Decimal × Int32);
dev `pass@execute` (Float64 × Int32) **or** the HAVING-scalar wall. **Record both raw rows verbatim** — they fix
the classifier + name the next ADR. Confirm keyed (the 3-table base-relation join). Don't leave probe code behind.

## D1 — fixtures: none new
`fn q11_tables(strict, sf)` over `partsupp` (`generate_partsupp`) + `supplier` (`generate_supplier`) + `nation`
(`generate_nation`); `facts_for_batch` each. No new columns (`ps_supplycost`/`ps_availqty`/`ps_suppkey`/
`ps_partkey`/`s_suppkey`/`s_nationkey`/`n_name`/`n_nationkey` all exist).

## D2 — wiring — `lib.rs` + `main.rs`
- `Q11_DEV_SQL` (official q11: `partsupp, supplier, nation` on `ps_suppkey = s_suppkey AND s_nationkey =
  n_nationkey AND n_name = 'GERMANY'`; `GROUP BY ps_partkey`; `value = SUM(ps_supplycost * ps_availqty)`;
  `HAVING value > (SELECT SUM(ps_supplycost * ps_availqty) * 0.0001 FROM <same join> WHERE n_name = 'GERMANY')`;
  `ORDER BY value DESC`); `STRICT_Q11_SQL = Q11_DEV_SQL`.
- `q11_tables`; `run_dev_q11`/`run_strict_q11` via `run_query_with_tables("q11", …, q11_tables(strict, sf))`.
- `status_rows()` — add `"q11"`; matrix row. `main.rs` — route `"q11"` (dev/strict).

## D3 — classifier
- If strict walls on the Decimal×Int multiply, it should classify as the existing **`unsupported_decimal_arithmetic`**
  (the "decimal … arithmetic operands" reject) — confirm it matches; no new reason needed if so.
- If a different wall appears (e.g. the HAVING-scalar in dev), add a **specific** reason matching its raw reject
  (narrow, before the generic buckets, no overclassification) + a unit test; else keep `fail(unrecognized@phase)`
  with the raw error documented (no broad classifier).

## Tests — `crates/toron-tpch/tests/harness.rs`
- `q11_dev_executes_strict_blocks_on_decimal_int_multiply` (or the measured shape): dev + strict at sf=0.01 assert
  the measured `Status`/`Phase`/`reason`. 64MB-stack thread if deep. If dev itself walls (HAVING-scalar), assert
  that precise row instead.
- **Keyed-at-default-scale** — the `partsupp ⋈ supplier ⋈ nation` join must be keyed at sf=0.01 (base-relation
  equi-join; not a cartesian) for whichever mode reaches execute (the ADR 311 habit).
- **No-regression** — existing reach (q01-10/12/13/14/16/17/20/22) + the 17 correctness cells stay green; no
  fixture change.

## Phase 3 — record for the forward arc
- Record (results doc): the measured dev + strict rows; that the strict wall is the **Decimal × Int-column
  multiply** (`ps_supplycost * ps_availqty`) → names **ADR 315** (Decimal × Int-column multiply/alignment); if dev
  reaches execute, its digest + non-emptiness for the future oracle.
- q11 counts as keyed-green reach only if both modes pass; document the split honestly otherwise.
