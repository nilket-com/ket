# Implementation Plan — ADR 274: tpch.q10 reachability attempt

## Summary
A harness reachability attempt (not an engine cut): add `nation` + an expanded, mode-sensitive `customer`,
wire the tpchgen-exact q10 SQL through the ADR 269 multi-table harness (q10 is its first 4-table user), run
dev + strict, classify the measured wall precisely, and record the measured row (expected:
dev `pass@execute`, strict `blocked(unsupported_decimal_group_key@execute)` if no earlier wall appears). Scope:
`crates/toron-tpch` only.

## Phase 0 — verify the board
`matrix` → q01/q03/q06/q14 `pass@execute`, q10 `not_run`; `correctness-matrix` → q06 `pass@compare`.

## Phase 1 — fixtures (`lib.rs`)
- **`nation`**: `nation_schema` (`n_nationkey` Int64, `n_name` Utf8, `n_regionkey` Int64), `nation_descriptor`
  (`TableObjectId::new([17; 16])`), `generate_nation(sf)` from `tpchgen::generators::NationGenerator` (25 rows;
  no decimals → identical dev/strict, like `part`).
- **`customer` expansion → mode-sensitive.** Append (after `c_mktsegment`, so q03 positions hold): `c_name`
  (Utf8), `c_acctbal` (`Float64` dev / `Decimal128(15,2)` strict), `c_address`/`c_phone`/`c_comment` (Utf8),
  `c_nationkey` (Int64). Split into `dev_customer_schema`/`strict_customer_schema` +
  `generate_dev_customer`/`generate_strict_customer` (mirror `lineitem`: `c_acctbal.as_f64()` vs
  `.into_inner() as i128` into `Decimal128(15,2)`), with a descriptor per schema. Route `q03_tables(strict, sf)`
  to the mode-appropriate customer (q03 ignores `c_acctbal` → its row + digest are unchanged).
- `orders`/`lineitem` reuse existing columns (`o_orderdate`, `o_custkey`, `o_orderkey`; `l_orderkey`,
  `l_returnflag`, `l_extendedprice`, `l_discount`) — no change.

## Phase 2 — q10 SQL (`lib.rs`)
`Q10_DEV_SQL` / `STRICT_Q10_SQL` = tpchgen Q10 with `:1` → `'1993-10-01'`, interval upper bound →
`DATE '1994-01-01'`, `ORDER BY revenue DESC` (no tiebreak, no LIMIT). Same text both modes.

## Phase 3 — wiring (`lib.rs` + `main.rs`)
- `run_dev_q10` / `run_strict_q10`: build four `HarnessTable`s (lineitem `TableId(1)`, customer `TableId(2)`,
  orders `TableId(3)`, nation `TableId(4)`) via `run_query_with_tables` (a `q10_tables(strict, sf)` helper, like
  `q03_tables`).
- CLI: `run --query q10 --mode dev|strict` (mirror the q03 arm). `status_rows` → q10 `implemented`.

## Phase 4 — measure + classifier (`telemetry.rs`)
- Run the full q10 attempt after fixture wiring. If strict q10 measures the Decimal group-key wall, add
  `"unsupported_decimal_group_key"` to `RECOGNIZED_BLOCKERS`, and in `reason_for_error` add — **before** the
  generic `else if lowered.contains("decimal")` (→ `unsupported_decimal_arrow`) arm:
  ```rust
  } else if lowered.contains("unsupported group by type") && lowered.contains("decimal") {
      "unsupported_decimal_group_key"
  }
  ```
  matching the executor's `group_value` error (`"unsupported GROUP BY type: Decimal128(15, 2)"`). Kept specific
  so it doesn't fall to the Decimal-carrier bucket (ADR 262 precise-match).
- Run `run --query q10 --mode dev|strict --allow-blocked` + `matrix`; record the measured row from the **full**
  q10 attempt. If it walls somewhere other than the group key, classify *that* (or honest `fail`) — don't force
  the predicted reason.

## Phase 5 — tests (`tests/harness.rs`)
- A q10 test matching the measured row: expected dev `pass@execute` (+ digest); expected strict `blocked` at
  `Phase::Execute` with reason `unsupported_decimal_group_key` if the measured wall is Decimal group keys;
  q10 `implemented` in `status`.
- If the Decimal group-key classifier lands, a `reason_for_error` unit assertion:
  `"unsupported GROUP BY type: Decimal128(15, 2)"` → `unsupported_decimal_group_key` (not
  `unsupported_decimal_arrow`).
- q01/q03/q06/q14 reachability tests + the q06 correctness test stay green (append-only customer).

```
scripts/cargo-cgroup run   -p toron-tpch -- matrix

git diff --check
```
Harness-only. If q10 measures the expected wall, ADR 275 is the `Decimal128` group-key engine cut, with the
full `-p toron` gate.

## Risk notes
- **Don't move q01/q03/q06/q14.** Append customer columns; route `q03_tables` to the mode-sensitive customer;
  the q03 row + q06 correctness cell stay unchanged.
- **Classify precisely.** If strict q10 = `unsupported_decimal_group_key@execute`, do not let it fall into the
  generic `unsupported_decimal_arrow`; verify against the *actual* measured reason, not the predicted one.
- **No engine feature.** strict stays `Decimal128`; the strict outcome is the honest measured deliverable.
- **Mode-sensitive customer is new.** q03's customer was identical dev/strict; q10's `c_acctbal` forces the
  split — confirm the strict `Decimal128(15,2)` `c_acctbal` raw scaling mirrors the lineitem money columns.
