# ADR 313 — tpch.q15 reachability

## Status
Proposed.

## Context

Board 17/17; q15 is the cleanest likely-green reach probe left — no fixture adds, mostly composing landed
surfaces. **Verify-first.** Even if it greens the reach value is high: q15 is the **first TPC-H cell using a CTE
relation as both a joined `FROM` source *and* the source of an uncorrelated aggregate scalar subquery**.

```sql
WITH revenue AS (
  SELECT l_suppkey AS supplier_no, SUM(l_extendedprice * (1 - l_discount)) AS total_revenue
  FROM lineitem
  WHERE l_shipdate >= DATE '1996-01-01' AND l_shipdate < DATE '1996-01-01' + INTERVAL '3' MONTH
  GROUP BY l_suppkey
)
SELECT s_suppkey, s_name, s_address, s_phone, total_revenue
FROM supplier, revenue
WHERE s_suppkey = supplier_no AND total_revenue = (SELECT MAX(total_revenue) FROM revenue)
ORDER BY s_suppkey
```

## Grounded feature inventory
- **CTE/WITH** non-recursive lowering exists (ADR 254; recursive is ADR 255); the body is `GROUP BY l_suppkey` +
  `SUM(discounted)` (q05/q07 territory).
- **`INTERVAL '3' MONTH`** landed + exercised (q04; `LoweredIntervalLiteral::CalendarMonths`, sql_planner:473);
  the `l_shipdate` range is a standard date filter (q01/q06).
- supplier ⋈ revenue (`s_suppkey = supplier_no`) equi-join; `ORDER BY s_suppkey`.
- All fixture columns exist (`s_name`/`s_address`/`s_phone`/`s_suppkey`, `l_shipdate`/`l_extendedprice`/
  `l_discount`/`l_suppkey`) — **no fixture adds**.

## The genuine verify-first risk
- **The CTE `revenue` is referenced twice** — in the outer `FROM` *and* in the scalar subquery `(SELECT MAX(...)
  FROM revenue)`. Whether the planner inlines/materializes a twice-referenced CTE is the open question.
- **The MAX-scalar-over-CTE + the `total_revenue = (SELECT MAX(...))` comparison** — a global-aggregate scalar
  subquery whose result is compared (Decimal `=` Decimal, same type) against the per-supplier revenue.

## Decision

Add q15 dev+strict, official shape (WITH-CTE form of the q15 view), `:1` date = `1996-01-01`. **Verify-first** —
measure the first wall; don't pre-solve. **Not mode-agnostic** — `total_revenue` is Decimal (strict) / Float64
(dev), so dev and strict digests differ; record both.

### D1 — fixtures (none new)
`q15_tables(strict, sf)` over `supplier` + `lineitem`, reusing existing builders. No new columns.

### D2 — wiring
`Q15_DEV_SQL`/`STRICT_Q15_SQL`; `q15_tables`; `run_dev_q15`/`run_strict_q15`; `status_rows`; `main.rs` routes
`"q15"`; matrix row.

### Verify-first — measure
Run q15 at sf=0.01; record the measured row. **Expected `pass@execute` both modes → reach 18.** Confirm **keyed
by plan shape**, not by timing alone: a q15 supplier × revenue cartesian is small enough at sf=0.01 to complete
quickly, so the harness needs a bind/plan assertion that `s_suppkey = supplier_no` becomes an `Inner` join key
rather than a keyless `Cross` plus residual filter. If a wall, the likeliest candidate is the **CTE
double-reference** or the **MAX-scalar-over-CTE**; classify it **precisely** (specific telemetry reason), no
pre-solve.

## Acceptance
- `q15 dev`/`strict` = `pass@execute` (sf=0.01) plus a discriminating keyed-plan assertion for the
  supplier/revenue join → reach **18**; or a precise measured wall naming the next ADR. Reach (other cells) +
  correctness (17) unchanged; **no fixture change**.
- `matrix` includes q15; a harness test pins the measured row. Documented in the results doc (incl. whether the
  result is non-empty, and **whether there are ties** — multiple suppliers at the max revenue — for the future q15
  correctness oracle, where the `= MAX` tie-set matters).

## Boundaries
- Reachability only; no q15 correctness oracle. No engine work expected; no fixtures. If a wall, classify precisely
  and defer the engine cut to its own ADR.

## Forward arc
If green → reach 18, and q15 becomes a correctness candidate (a new shape: CTE-as-both-FROM-and-scalar-source +
global-MAX scalar subquery + the `= MAX` tie-set + revenue-SUM-by-supplier). q11 remains likely-green coverage;
q19 (disjunctive) / q21 (triple self-join) are the heavier walls.

## Why toron-home / harness
A `toron-tpch` reachability addition (query + wiring); no `crates/toron` engine change expected, no fixture change,
no Wendelon / cross-ring surface.
