# ADR 314 — tpch.q11 reachability

## Status
Proposed.

## Context

q11 reach, verify-first. The "likely cheap coverage" expectation is **corrected by grounding**: q11 has a real
candidate wall — `ps_supplycost * ps_availqty` is the rail's first **Decimal × Int-column** multiply. q11 likely
follows the same split pattern q09 exposed before ADR 302 (dev green / strict blocked), not a clean green. (The
q15 lesson: measure, don't predict-green.)

```sql
SELECT ps_partkey, SUM(ps_supplycost * ps_availqty) AS value
FROM partsupp, supplier, nation
WHERE ps_suppkey = s_suppkey AND s_nationkey = n_nationkey AND n_name = 'GERMANY'
GROUP BY ps_partkey
HAVING SUM(ps_supplycost * ps_availqty) > (
  SELECT SUM(ps_supplycost * ps_availqty) * 0.0001
  FROM partsupp, supplier, nation
  WHERE ps_suppkey = s_suppkey AND s_nationkey = n_nationkey AND n_name = 'GERMANY'
)
ORDER BY value DESC
```

## Grounded candidate walls (measure the order)
1. **`ps_supplycost * ps_availqty` — Decimal-col × Int-col multiply (the likely STRICT first wall).**
   `ps_supplycost` is `Decimal128(15,2)` (strict) / `Float64` (dev); `ps_availqty` is **`Int32`**. The Mul arm is
   `Decimal128 * Decimal128` (ADR 263); ADR 266 coerces only Int/Float **literals** → Decimal, not **columns**.
   So strict `Decimal-col * Int-col` falls to `arithmetic_output_type` →
   `unsupported_decimal_arithmetic` ("operands must be Int/Float, got Decimal128 and Int32"). **Dev**
   (`Float64 * Int32`) coerces fine → likely green. This is the old q09 split shape: dev green, strict
   `unsupported_decimal_arithmetic@bind`.
2. **The HAVING scalar subquery** (`value > (SELECT SUM(...) * 0.0001 …)`) — a non-correlated global-SUM scalar
   recombined above the aggregate through the existing scalar pull-up path. The likely **DEV** candidate once
   strict walls early on (1).
3. The `* 0.0001` Decimal-fraction multiply on the scalar + the `value > threshold` Decimal comparison
   (283/286/302 surfaces). Behind (1)/(2).
- Fixtures all exist (`ps_supplycost`/`ps_availqty`/`ps_suppkey`/`ps_partkey`/`s_suppkey`/`s_nationkey`/`n_name`/
  `n_nationkey`) — **no fixture adds**. The join is `partsupp ⋈ supplier ⋈ nation` (base relations, q05/q07
  territory — keyable, unlike q15's composite). The scalar subquery is a **repeated FROM, not a CTE** — no
  q15-style composite issue.

## Decision

Add q11 dev+strict, official shape, `:1` nation = `'GERMANY'`, `:2` fraction = `0.0001`, `STRICT_Q11_SQL =
Q11_DEV_SQL`. **Verify-first** — measure both modes; don't pre-solve. **Not mode-agnostic** (`value`
Decimal/Float64).

### D1 — fixtures (none new)
`q11_tables(strict, sf)` over `partsupp` + `supplier` + `nation`, reusing existing builders.

### D2 — wiring
`Q11_DEV_SQL`/`STRICT_Q11_SQL`; `q11_tables`; `run_dev_q11`/`run_strict_q11`; `status_rows`; `main.rs` routes
`"q11"`; matrix row.

### Verify-first — measure
Run q11 at sf=0.01 both modes; record the rows. **Expected split:** dev = `pass@execute` (or the HAVING-scalar
wall), strict = `blocked(unsupported_decimal_arithmetic@bind)` on `Decimal × Int`. Confirm **keyed** (the 3-table
join is base-relation; not a cartesian). Classify any wall **precisely** (reuse `unsupported_decimal_arithmetic` if
it's the Decimal×Int multiply; a new precise reason if the HAVING-scalar). No pre-solve.

## Acceptance
- q11 dev/strict record **precise** measured rows at sf=0.01 — likely dev green / strict
  `unsupported_decimal_arithmetic`. q11 counts as a keyed-green reach cell only if **both** modes pass; otherwise
  it's a measured red row (the split). Reach + correctness cells unchanged accordingly. **No fixture change.**
- `matrix` includes q11; a harness test pins the measured rows. Documented in the results doc (the split + the
  next ADR; and — only if it reaches execute — non-emptiness for the future oracle).

## Boundaries
- Reachability only; no q11 correctness oracle. No engine work in this cut. If a wall (expected), classify
  precisely and defer the engine cut to its own ADR.

## Forward arc
Likely **ADR 315 = Decimal × Int-column multiply/alignment** — the non-literal analogue of the decimal literal
coercions already used by earlier Decimal slices. The implementation must derive the output `(p,s)` from the code
and tests, not from this reach ADR. Then q11 re-measures (the HAVING-scalar / the `* 0.0001` fraction → further
ADRs). q19/q21 still need their own reach probes; q15's composite-join is its own engine ADR.

## Why toron-home / harness
A `toron-tpch` reachability addition (query + wiring); no `crates/toron` engine change in this cut. The Decimal×Int
multiply (if measured) is a separate engine ADR. No Wendelon / cross-ring surface.

## Council provenance
q11 reach is a go (operator + Codex, hybrid cadence: reach-first per query, correctness soon after a new-machinery
green, fix only measured walls). Grounding corrected the "likely cheap" framing — the Decimal×Int-column multiply
is a real candidate wall. No fixture adds; base-relation keyable join (not q15's composite); verify-first;
precise-classifier-if-wall; the Decimal×Int multiply/alignment names the likely ADR 315.
