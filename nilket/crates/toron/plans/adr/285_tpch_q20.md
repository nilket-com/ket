# ADR 285 — tpch.q20 reachability (nested membership composition)

## Status
Proposed.

## Context

Reach board after ADR 284: q01/q02/q03/q04/q05/q06/q10/q14/q17 `pass@execute` both modes (9); correctness rail
q06/q01/q03 (3). q20 is the reach frontier's next subquery-composition probe — nested membership plus a
correlated aggregate scalar **inside a membership subquery body**:

```sql
SELECT s_name, s_address FROM supplier, nation
WHERE s_suppkey IN (
  SELECT ps_suppkey FROM partsupp
  WHERE ps_partkey IN (SELECT p_partkey FROM part WHERE p_name LIKE 'forest%')
    AND ps_availqty > (SELECT 0.5 * SUM(l_quantity) FROM lineitem
      WHERE l_partkey = ps_partkey AND l_suppkey = ps_suppkey
        AND l_shipdate >= DATE '1994-01-01' AND l_shipdate < DATE '1995-01-01')
) AND s_nationkey = n_nationkey AND n_name = 'CANADA'
ORDER BY s_name
```

**Concrete first wall = the membership subquery body** (grounded 3/3). The outer
`s_suppkey IN (SELECT ps_suppkey FROM partsupp WHERE …)` is an *uncorrelated* IN (partsupp doesn't reference
supplier), but its WHERE carries a **nested IN** (`ps_partkey IN (…)`) and a **correlated scalar**
(`ps_availqty > (SELECT …)`). `lower_membership_subquery` (`sql_planner.rs:5431`) lowers that WHERE via the
restricted `classify_exists_conjunct` path (an outer-correlation equi-pair, or an inner residual lowered with
`lower_expr`). A nested `IN`-subquery is a join transform (not a value `Expr`); a scalar subquery is not a
residual — both reject.

Two-key correlation is **not** the wall: `bind_deferred_scalar_subquery` collects correlation `pairs` into a
`Vec` and groups by all inner keys, so `l_partkey = ps_partkey AND l_suppkey = ps_suppkey` recombine is supported.

## Decision

q20 = an engine cut (D1) + a small harness cut (D2).

### D1 — compose subqueries inside an uncorrelated membership body
Generalize `lower_membership_subquery` so an **uncorrelated** membership body's WHERE goes through the standard
SELECT **filtering** pipeline, **filtering the existing body plan** (not lowering the membership subquery as a
projected derived SELECT — that would reshape the right-side scope the membership key extraction relies on):

1. Lower the body `FROM` as today (single source; q20's body is `FROM partsupp`). Broader membership-body FROM
   lists stay deferred.
2. Detect whether the body's top-level WHERE carries a qualified reference to the membership outer query.
   - If yes, keep the existing restricted `classify_exists_conjunct` path for the whole body (ADR 259 correlated
     membership preserved; correlated membership plus nested body subqueries stays deferred).
   - If no, the body is local to the membership subquery and may use the full filtering pipeline.
3. For the uncorrelated body, run the whole body selection through the filtering pipeline on the body plan:
   `pull_up_scalar_subqueries` (**outer scope = the body's qualifiers**, not the membership outer — q20's scalar
   correlates to `partsupp`, and the uncorrelated body must not let a scalar reach the membership outer),
   `join_scalar_subplans`, then `lower_where` (so a nested `IN`/`EXISTS` composes recursively).
4. Extract the single projected membership key as today; the semi/anti-join construction is unchanged.

Downstream composes via existing machinery, no new IR: nested `ps_partkey IN (…)` → ADR 256 uncorrelated
semi-join (recursively); `ps_availqty > (SELECT 0.5 * SUM …)` → ADR 282/260 deferred decorrelation correlated to
the body's `partsupp`, two-key `Vec` recombine, `0.5 *` wrapper riding the rewritten outer expression; ADR 284's
multi-table-inner + inner-cartesian keying covers the scalar's inner shape.

### D2 — q20 harness
Append `p_name` (Utf8) to `part` (the only fixture delta — `partsupp`/`supplier`/`nation`/`lineitem` columns
exist from q02/q05/q17). Official q20 SQL, params literalized (`'forest%'`, `'CANADA'`); literalize the
`l_shipdate` upper bound (`< DATE '1995-01-01'`) per the q05/q10/q14 convention (interval runtime stays its own
deferred row). `q20_tables` loads **supplier, nation, partsupp, part, lineitem** (q20 references no `region`);
`run_dev_q20`/`run_strict_q20`, CLI route, status inventory, matrix row, harness test; `facts_for_batch` on every
table.

## Scope honesty — likely a 2-ADR arc
ADR 285 clears the membership-body composition (the measured first wall). If a further wall remains it is
measured and named **ADR 286** — not smuggled. The **concrete predicted second wall** is
`ps_availqty > 0.5 * SUM(l_quantity)`: `ps_availqty` is `Int32`, the scalar side is `Float64` (dev) / `Decimal`
(strict). Comparison binding handles literal coercion and (ADR 283) Decimal-vs-Decimal scale alignment, but not
general **non-literal** alignment between an integer column and a Float/Decimal expression — that would be ADR 286.

## Boundaries
- Official q20 SQL unchanged; literalize only the date upper bound.
- D1 generalizes the **uncorrelated** membership body; correlated-IN-with-nested-subqueries and `NOT IN` nesting
  stay named deferred siblings (don't complicate the null-aware anti-join desugar). No broad membership
  broadening beyond q20's shape.
- Reachability, not q20 answer-correctness. Interval runtime arithmetic deferred. No `substring` surface (q22).
  No new IR.

## Acceptance (tiered)
- **Minimum:** q20 advances off the membership-body reject (nested IN + correlated scalar compose inside the IN
  body).
- **Target:** `q20 dev=pass@execute   strict=pass@execute`, **tractable at `sf=0.01`** both modes (joins keyed,
  not cartesian — the q02/ADR 284 lever) under the q05/q10 explicit-large-stack pattern.
- **Honest-red fallback:** a further wall is a precise `blocked(reason@phase)` naming ADR 286 (likely the Int32
  vs Float/Decimal comparison alignment above) — no broad `UnknownColumn`/generic allowlisting; no hollow
  tiny-scale green.
- Existing reach (9) + correctness (3) cells unchanged.

## Forward arc
ADR 286 if a q20 wall remains (the predicted numeric-alignment wall). Then q05 / q17 correctness (the reach/rail
gap is 9 vs 3) or q22 (`substring`) on reach.

## Why toron-home
Binder/planner subquery-composition generalization in `crates/toron` + a `toron-tpch` harness (`part.p_name` +
q20 wiring). No Wendelon / cross-ring surface.

## Council provenance
3/3 on q20 (Claude, Codex, Antigravity). The membership-body first wall is the grounded refinement of the seed's
"measure the wall." Two convergences resolved at synthesis: (1) **filter the body, don't project it as a derived
SELECT** (Codex's grounding — projecting reshapes the membership key scope); (2) the scalar pull-up's outer scope
is the **body's qualifiers**, not the union with the membership outer (Codex over Antigravity — the uncorrelated
body must not permit a scalar to correlate past it to supplier/nation). Codex's concrete second-wall prediction
(Int32-vs-Float/Decimal alignment → ADR 286) is recorded. The reach-vs-rail fork (q05 correctness, 9-vs-3 gap)
was surfaced; the council kept frontier momentum, with q05 the named next rail step.
