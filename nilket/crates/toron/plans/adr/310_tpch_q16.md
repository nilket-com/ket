# ADR 310 — tpch.q16 reachability

## Status
Proposed.

## Context

(ADR 309 is q13 correctness, sealed — this is **310**.) Board 16/16; the 2:1 cadence is retired, so this is a
straight reach probe. q16 is the cleanest likely-green of the remaining six: no fixture column appears missing,
and each operator family has landed precedent. The implementation still measures the row first; the green is a
hypothesis until the harness emits it.

```sql
SELECT p_brand, p_type, p_size, COUNT(DISTINCT ps_suppkey) AS supplier_cnt
FROM partsupp, part
WHERE p_partkey = ps_partkey
  AND p_brand <> 'Brand#45'
  AND p_type NOT LIKE 'MEDIUM POLISHED%'
  AND p_size IN (49, 14, 23, 45, 19, 3, 36, 9)
  AND ps_suppkey NOT IN (SELECT s_suppkey FROM supplier WHERE s_comment LIKE '%Customer%Complaints%')
GROUP BY p_brand, p_type, p_size
ORDER BY supplier_cnt DESC, p_brand, p_type, p_size
```

## Grounded feature inventory
- equi-join `partsupp ⋈ part`; `<>` filter; `NOT LIKE 'MEDIUM POLISHED%'` (prefix); `p_size IN (…)` (Int32 IN-list);
- `ps_suppkey NOT IN (SELECT …)` — an uncorrelated null-aware anti-semijoin (ADR 258/259 precedent); the inner
  `s_comment LIKE '%Customer%Complaints%'` is a multi-wildcard LIKE (q13 precedent);
- `COUNT(DISTINCT ps_suppkey)` per group (`build_distinct_aggregate_rewrite` / `DistinctAggregateRewrite`);
  `GROUP BY` (3 keys);
- 4-key `ORDER BY supplier_cnt DESC, p_brand, p_type, p_size` (1 DESC + 3 ASC) — ordering by the aggregate
  alias `supplier_cnt` (q13 `ORDER BY custdist` precedent).
- All fixture columns exist (`p_partkey`/`p_brand`/`p_type`/`p_size`/`ps_partkey`/`ps_suppkey`/`s_suppkey`/
  `s_comment`).

## Decision

Add q16 dev+strict, official shape, `STRICT_Q16_SQL = Q16_DEV_SQL`. **Verify-first** — measure the first wall, do
not pre-solve. q16 is mode-agnostic at the output surface (strings + Int32 + a count, no projected decimals), so
dev and strict are expected to match but still recorded separately.

### D1 — fixtures (none new)
`q16_tables(strict, sf)` over `part` + `partsupp` + `supplier` (the NOT-IN target), reusing existing builders. No
new columns.

### D2 — wiring
`Q16_DEV_SQL`/`STRICT_Q16_SQL`; `q16_tables`; `run_dev_q16`/`run_strict_q16`; `status_rows`; `main.rs` routes
`"q16"`; matrix row.

### Verify-first — measure
Run q16 at sf=0.01; record the measured row. Expected outcome is `pass@execute` in both modes, moving reach to 17.
Confirm keyed execution (partsupp ⋈ part is an equi-join, not a cartesian). If a wall appears, the likely candidates
are `COUNT(DISTINCT)` in the grouped + NOT-IN context or the null-aware anti-semijoin composition; classify only a
precise, query-independent blocker and do not pre-solve it inside this harness cut.

## Acceptance
- `q16 dev`/`strict` = `pass@execute` (keyed, sf=0.01) → reach **17**; or a precise measured wall naming the next
  ADR. Reach (other cells) + correctness (16) unchanged; **no fixture change**.
- `matrix` includes q16; a harness test pins the measured row. Documented in the results doc (incl. whether the
  result is non-empty + whether the `NOT IN` actually excludes ≥1 supplier live — for the future q16 correctness
  oracle).

## Boundaries
- Reachability only; no q16 correctness oracle. No engine work expected; no fixtures. If a wall, classify precisely
  and defer the engine cut to its own ADR.

## Forward arc
If green → reach 17, and q16 becomes a correctness candidate (a new shape: `COUNT(DISTINCT)` per group + a NOT-IN
anti-semijoin + multi-wildcard LIKE). Then q11 / q15 (the other likely-green coverage), then the meaty walls q19
(disjunctive) / q21 (triple self-join).

## Why toron-home / harness
A `toron-tpch` reachability addition (query + wiring); no `crates/toron` engine change expected, no fixture change,
no Wendelon / cross-ring surface.
