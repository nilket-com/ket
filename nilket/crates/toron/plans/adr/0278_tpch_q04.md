# ADR 278 — tpch.q04 reachability attempt (correlated EXISTS + official date-interval)

## Status
Proposed.

## Context
The gauge has six reach cells dev+strict green (q01/q03/q05/q06/q10/q14 — q05 closed the join-shape frontier
through 6 tables) and two correctness cells (q06, q01). Per the operator's steer, the next *reach* ADR lets a
remaining **hard class** nominate itself rather than re-measuring a covered join shape. **tpch.q04** (Order
Priority) is the cleanest such probe: the gauge's first **correlated-subquery** query, and — keeping the
official interval — its first official **`Date32 + CalendarMonthInterval`** expression. It needs no new table:
only appended columns on the existing orders/lineitem. A reachability attempt in the ADR 269/272/274/277 mold:
bring q04 in, run dev + strict, record the first wall; implement nothing. (Council-selected topic.)

q04 shape (tpchgen-2.0.2's exact Q4, `:1` → `'1993-07-01'`, **interval kept official**, no LIMIT):
```sql
SELECT o_orderpriority, COUNT(*) AS order_count
FROM orders
WHERE o_orderdate >= DATE '1993-07-01' AND o_orderdate < DATE '1993-07-01' + INTERVAL '3' MONTH
  AND EXISTS (SELECT * FROM lineitem
              WHERE l_orderkey = o_orderkey AND l_commitdate < l_receiptdate)
GROUP BY o_orderpriority
ORDER BY o_orderpriority
```

## Two co-candidate first walls (verify-first — the impl measures plan + bind + execute)
q04 deliberately carries **both** new classes; the pipeline hits one first and the matrix records it. That's the
gauge working, not noise — this is a reachability gauge, not a unit test for one operator.

- **Correlated EXISTS — q04's *unqualified* correlated ref.** Toron has correlated-EXISTS decorrelation
  (`SqlExpr::Exists` → a `LeftSemi`/`LeftAnti` desugar), but it classifies the correlated pair **by column
  qualifier** (`classify_exists_conjunct` over the outer/inner qualifier sets), and every
  `exists_decorrelation_test` uses *qualified* refs (`fact.pk = fact.k`). q04's predicate is **unqualified** —
  `l_orderkey = o_orderkey` — so the classifier may not resolve which side each column is on and reject it: a
  precise red row (correlated EXISTS needs qualified refs / unqualified-correlated resolution unsupported)
  naming the decorrelation-gap ADR. If it instead resolves the distinct `l_`/`o_` names by scope, the EXISTS
  lowers to a semi-join.
- **Date-interval — `Date32 + INTERVAL '3' MONTH`.** With the official bound, the outer filter exercises the
  SQL `Date32 + CalendarMonthInterval` path the gauge has literalized around until now. Because both operands
  are literals, this may fold during bind rather than reach the runtime Date32 interval kernel; either way, if
  the official expression walls, that's q04's correct first red row, naming the date-interval ADR. Literalizing
  it would be honest only if the feature were known absent and would mask the probe — true earlier in the arc,
  not now; so q04 keeps the real shape.

Everything else is covered: `COUNT(*)` + `GROUP BY o_orderpriority` (Utf8), `ORDER BY o_orderpriority`, the
orders/lineitem fixtures.

## Decision
Bring q04 into the gauge as a measured row in **both** modes; implement no wall.

1. **q04 SQL, tpchgen-exact, official interval.** `:1` → `'1993-07-01'`, `o_orderdate < DATE '1993-07-01' +
   INTERVAL '3' MONTH` kept official, `ORDER BY o_orderpriority` only — no LIMIT. Same text both modes.
2. **Fixtures (append-only — no new table).** Append `o_orderpriority` (Utf8) to the orders fixture; append
   `l_commitdate` + `l_receiptdate` (`Date32`, via `to_unix_epoch`) to the dev + strict lineitem fixtures.
   Existing queries reference none of these, so their outputs/digests + the q06/q01 correctness cells stay
   stable. orders/lineitem are otherwise reused; q04's tables are orders + the EXISTS-subquery lineitem.
3. **Wire + measure precisely (ADR 262).** `run_dev_q04` / `run_strict_q04`, CLI `--query q04`, `status_rows`
   → q04 `implemented`. Run both modes; honest row — `pass`, a **specific** recognized blocker, or an honest
   `fail`. The measured first wall (interval or correlated EXISTS) names the next ADR; classify it precisely,
   not under a generic bucket.

## Watch-items (operator) → guards
- **Append-only fixtures.** `o_orderpriority`/`l_commitdate`/`l_receiptdate` appended at the end; the six
  reach cells + q06/q01 correctness stay unchanged (verify the existing tests stay green).
- **Keep the real shape.** Official interval, canonical EXISTS — no literalizing or rewriting to dodge a wall
  (the feature is no longer known-absent). The measured first wall is the deliverable.
- **No engine feature.** Nothing added to force q04 through; a measured wall names the next ADR.
- **`status` stays static inventory** (q04 → `implemented`); the measured row lives only in the matrix.
- **Test stack.** q04 is a 2-relation semi-join — try a bare `#[tokio::test]` first; if the decorrelated
  future overflows libtest's default test stack (as 4-/6-table did), move to the explicit
  `std::thread::Builder` stack-size wrapper.

## Acceptance
- q04 moves `not_run` → a measured row (pass | specific recognized blocker | honest fail) in both modes; the
  reachability matrix + a harness test render it.
- If blocked, the reason is allowlisted with a precise classifier and names the next ADR (decorrelation or
  date-interval, per the measured wall).
- q01/q03/q05/q06/q10/q14 reachability + the q06/q01 correctness cells are unchanged.

## Forward arc
The measured first wall decides: a date-interval wall → the `Date32 + CalendarMonthInterval` ADR; an
unqualified correlated-EXISTS wall → the decorrelation-generality ADR; a pass → the gauge's first subquery
cell, with runtime interval coverage and the harder correlated forms (q17/q20 scalar/`IN`, q22) remaining. A
q03/q05 correctness oracle stays available on the correctness rail.

## Why toron-home
The `toron-tpch` reachability gauge + whatever binder/decorrelation/exec wall q04 surfaces. No cross-ring
surface.
