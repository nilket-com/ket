# ADR 284 — tpch.q02 reachability (multi-table-inner correlated scalar)

## Status
Proposed.

## Context

Reach board after ADR 283: q01/q03/q04/q05/q06/q10/q14/q17 `pass@execute` both modes; q02… not_run; correctness
rail q06/q01/q03. q02 is the correlated-scalar frontier's next generalization. q17 proved a **single-table-inner**
unqualified correlated scalar (`0.2 * AVG(l_quantity)`); q02's scalar is `MIN(ps_supplycost)` over a **multi-table
inner** (`partsupp, supplier, nation, region`), compared `ps_supplycost = (SELECT MIN(...) …)`, with a bare
correlation (`p_partkey = ps_partkey`) → the ADR 282 deferred path.

**This is an engine cut, not harness-only.** `validate_aggregate_scalar_subquery_shape` currently hard-requires
`select.from.len() == 1`, and both scalar lowerings use `from[0]` only. q02's 4-table inner is rejected there
(`"non-aggregate scalar subqueries are not supported"`) before the partsupp data matters.

## Decision

Implement q02 as an engine cut (D1) plus a harness fixture cut (D2).

### D1 — generalize the correlated-scalar inner to a multi-table comma-join
Three parts; the third is the non-obvious tractability invariant.

1. **Split the scalar-subquery gate.** Separate "is this a supported scalar-aggregate shape?" (one
   aggregate-bearing projection; no GROUP BY/HAVING/DISTINCT; aggregate args not outer-correlated; not a
   non-aggregate scalar) from "is this the older single-source lowering?". The **deferred-correlated** path may
   accept a comma-list inner `FROM` (still rejecting explicit `from[i].joins` — JOIN syntax stays deferred). The
   uncorrelated (ADR 257) and qualified-resolved paths keep the single-source gate unless their inner lowering is
   generalized in lockstep (so the relaxed gate can never silently drop `from[1..]`).
2. **Lower the full inner `FROM`.** Replace the `from[0]`-only lowering on the deferred branch with a left-deep
   comma-join over `select.from` — preferably by extracting a shared helper from `lower_select`'s existing FROM
   lowering rather than copying the fold (preserving its join-chain behavior). The deferred branch already
   collects the whole inner `WHERE` into `predicates`; ADR 282's binder classifier then routes each by
   outer-ownership: the correlation pair (`p_partkey = ps_partkey`) → recombine key; the inner-only predicates
   (inner joins `s_suppkey = ps_suppkey`, `n_nationkey`, `r_regionkey` + filter `r_name = 'EUROPE'`) → inner
   residual. No classifier change, no new IR (`DeferredScalarSubquery.inner` already holds an arbitrary plan).
3. **Key the inner comma-join — the ADR-282 cartesian trap, on the inner.**
   `recognize_cross_equi_joins` runs once at the *top* of `bind`, where the deferred node's `inner` is still a
   bare `Cross` and its residual predicates live in a `Vec`, invisible to the recognizer.
   `bind_deferred_scalar_subquery` only *later* builds `Filter(inner-residuals, Cross(partsupp,supplier,nation,
   region))` — so the inner 4-table comma-join would bind as a **materialized cartesian** (a q02-scale blowup, the
   same class ADR 282 fixed for the outer). The binder must **re-run `recognize_cross_equi_joins` on the
   constructed inner-residual-filtered plan** so the inner joins lift to keyed inner joins before the group-by.
   (Single-table q17 never hit this — no inner `Cross`.) `MIN(Decimal)` (identity-typed) and
   `ps_supplycost = MIN(...)` (same-`(p,s)` Decimal `=`, ADR 283 reconcile a no-op) are expected to compose —
   measured, not asserted.

### D2 — q02 harness (fixtures + SQL + wiring)
First `partsupp` fixture (`ps_partkey` Int64, `ps_suppkey` Int64, `ps_availqty` Int32; `ps_supplycost` Float64
dev / **Decimal128(15,2) strict**; `ps_comment` omitted — q02 doesn't reference it). Append (append-only, so
prior digests stay stable): `part` += `p_size` Int32, `p_mfgr` Utf8; `supplier` += `s_acctbal`
(Float64/Decimal128(15,2)), `s_name`/`s_address`/`s_phone`/`s_comment` Utf8. Official q02 SQL (`p_size = 15`,
`p_type LIKE '%BRASS'`, `r_name = 'EUROPE'`, the `ORDER BY`, no LIMIT); `run_dev_q02`/`run_strict_q02`, CLI route,
status inventory, matrix row, harness test. `facts_for_batch` on every q02 table (ADR 270: missing facts turn a
fair query into a fixture artifact).

## Boundaries
- Official q02 SQL unchanged — no pre-qualification, no scalar rewrite, no LIMIT, inner filters intact.
- Strict keeps official Decimal types (`ps_supplycost`, `s_acctbal`) — no Float64 shortcut. Append-only columns.
- D1 generalizes only the **deferred correlated-scalar** path; uncorrelated/qualified paths stay correct under
  the split gate.
- No public `CAST`/string-function surface; no cost-based join reordering claim (goal: keyed execution).
- Reachability, not q02 answer-correctness (a q02 oracle is a later rail item). No q22/q20/q17/q05 in this cut.

## Acceptance (tiered)
- **Minimum:** q02 advances off the `from.len()==1` reject (the multi-table-inner scalar binds).
- **Target:** `q02 dev=pass@execute   strict=pass@execute`, **tractable at `sf=0.01`** in both modes (proves the
  inner comma-join is keyed, not a cartesian — D1 #3), under the q10/q05 explicit-large-stack test pattern.
- **Honest-red fallback:** a further wall (post-D1) is a precise `blocked(reason@phase)` naming ADR 285 — no
  broad `UnknownColumn`/generic allowlisting; no hollow tiny-scale green.
- Existing reach (q01/q03/q04/q05/q06/q10/q14/q17) and correctness (q01/q03/q06) cells unchanged.

## Forward arc
q22 (`substring` — verified absent) / q20 (nested membership) on reach; q05 or q17 correctness on the rail; a q02
correctness oracle once strict-green. A post-D1 wall names ADR 285.

## Why toron-home
Binder + planner engine generalization in `crates/toron`, plus a `toron-tpch` harness (new `partsupp` fixture +
q02 wiring). No Wendelon / cross-ring surface.
