# ADR 274 — tpch.q10 reachability attempt (4-table; likely Decimal-group-key wall)

## Status
Proposed.

## Context
After ADR 273 the reachability gauge is q01/q03/q06/q14 `pass@execute` (both modes) and the correctness rail
has its first cell (q06 strict `pass@compare`). Per the 273 cadence — *a couple of reach cells, then a
correctness cell* — ADR 274 returns to reachability with **tpch.q10** (Returned Item Reporting), the first
**4-table** query. It's the smallest step over q03: reuse customer/orders/lineitem, add only the 25-row
`nation` lookup, exercise ADR 270's n-ary recognition at 4 tables, and — the interesting part — group by a
**numeric key**. (q05's 6-table and the q01 correctness oracle defer.)

q10 shape (tpchgen-2.0.2's exact Q10, `:1` → `'1993-10-01'`, interval upper bound literalized, **`ORDER BY
revenue DESC` only — no tiebreak, no LIMIT**):
```sql
SELECT c_custkey, c_name, SUM(l_extendedprice * (1 - l_discount)) AS revenue,
       c_acctbal, n_name, c_address, c_phone, c_comment
FROM customer, orders, lineitem, nation
WHERE c_custkey = o_custkey AND l_orderkey = o_orderkey
  AND o_orderdate >= DATE '1993-10-01' AND o_orderdate < DATE '1994-01-01'
  AND l_returnflag = 'R' AND c_nationkey = n_nationkey
GROUP BY c_custkey, c_name, c_acctbal, c_phone, n_name, c_address, c_comment
ORDER BY revenue DESC
```

## Grounded wall shortlist (verify-first)
The likely strict wall is grounded to the code: `exec.rs::group_value` has group-key arms for Bool/Int32/Int64/
**Float32/Float64** (`canonical_group_f*_bits`)/Date32/Timestamp/Utf8, and falls through to
`format!("unsupported GROUP BY type: {:?}", array.data_type())` for everything else — **there is no
`Decimal128` group-key arm**. q10 groups by `c_acctbal`, a `TPCHDecimal` → `Float64` (dev) / `Decimal128(15,2)`
(strict). So the expected row, if no earlier wall appears, is:
```
q10 dev    = pass@execute                                     (Float64 group key — supported)
q10 strict = blocked(unsupported_decimal_group_key@execute)   (Decimal128 group key — no arm)
```
The 4-table join is *not* the wall (ADR 270's recursive routing lifts `c_custkey=o_custkey`,
`l_orderkey=o_orderkey`, `c_nationkey=n_nationkey`; q03 proved a real 3-table shape), nor is the revenue
arithmetic (q01/q03/271). The implementation still measures the full q10 attempt — if strict q10 passes, the
board gains a fifth reach cell; if it walls elsewhere, that measured row names the next ADR.

## Decision
Bring q10 into the gauge as a measured row in **both** modes; implement no wall. (Council-selected topic.)

1. **q10 SQL, tpchgen-exact.** Interval literalized (`< DATE '1994-01-01'`), `ORDER BY revenue DESC` only — no
   tiebreak, no LIMIT (the bundled text carries none). Same text both modes; only `lineitem`/`customer`
   physical types differ. Don't rewrite to dodge the wall.
2. **Fixtures.** Add `nation` (`n_nationkey`, `n_name`, `n_regionkey`) via `NationGenerator`. **Expand
   `customer`** with `c_name`, `c_acctbal`, `c_address`, `c_phone`, `c_comment`, `c_nationkey`, **appended**
   after `c_mktsegment` so q03's columns/positions don't move. `c_acctbal` makes `customer` **mode-sensitive**
   (`Float64` dev / `Decimal128(15,2)` strict) — split it into dev/strict variants like `lineitem`, and route
   `q03_tables` to the mode-appropriate one (q03 ignores `c_acctbal`, so its row/digest are unchanged).
3. **Classify the measured wall precisely (ADR 262).** If strict q10 measures the Decimal group-key wall, add a
   `unsupported_decimal_group_key` recognized blocker + classifier matching `"unsupported group by type"` and
   `"decimal"`, placed **before** the generic `unsupported_decimal_arrow` Decimal-carrier bucket (which would
   otherwise mis-absorb this group-key gap). If q10 walls elsewhere, classify that measured reason precisely
   or leave it as an honest `fail`. This is a harness classifier, not an engine feature.

## Watch-items (operator) → guards
- **No engine feature.** Nothing added to make strict q10 pass; strict stays `Decimal128`. The measured strict
  outcome is the honest deliverable, not a thing to fix here.
- **Precise classification, not the generic bucket.** If strict q10 hits Decimal group keys, its reason is
  `unsupported_decimal_group_key`, not `unsupported_decimal_arrow`; an unrecognized error stays `fail`. A test
  pins the measured reason.
- **Append-only customer.** New columns appended after `c_mktsegment`; q03's row + the q06 correctness cell are
  unchanged after `customer` becomes mode-sensitive.
- **`status` stays static inventory** (q10 → `implemented`); the measured row lives only in the matrix.

## Acceptance
- q10 moves `not_run` → a measured row (pass | specific recognized blocker | honest fail) in both modes; the
  reachability matrix + a harness test render it (expected: dev `pass@execute`, strict
  `blocked(unsupported_decimal_group_key@execute)`).
- If strict q10 blocks on Decimal group keys, the strict reason is allowlisted with the precise classifier and
  **names ADR 275** (Decimal group-key support). If it blocks elsewhere, that measured reason names the next
  ADR.
- q01/q03/q06/q14 reachability and the q06 correctness cell are unchanged.

## Forward arc
If strict q10's measured wall is Decimal group keys, it names **ADR 275 — Decimal group-key support** (a
`Decimal128` arm in `exec.rs::group_value`/`group_column` — the engine cut that turns strict q10 green). If q10
passes or walls elsewhere, follow the measured row. The cadence then points to a correctness cell (q01 oracle —
grouped output, the first multi-row answer-check) before q05 (6-table). Correlated-subquery
(q04/q17/q20/q22) and date-interval arithmetic remain named, separate arcs.

## Why toron-home
The `toron-tpch` reachability gauge + the binder/exec wall it surfaces. No cross-ring surface.
