# ADR 272 — tpch.q03 (first 3-table reachability attempt)

## Status
Proposed.

## Context
After ADR 271 the matrix is q01/q06/q14 `pass@execute` (both modes); every other query
(q02-q05, q07-q13, q15-q22) is `not_run`. There is **no measured red row to inherit**, so the gauge advances
the way ADR 269 did: a **reachability attempt** — bring the next query into the harness, run it dev + strict,
and record whichever wall it hits first. The measured row names the next feature ADR; this cut **implements no
wall.**

The council (3-of-3) picked **tpch.q03** — the smallest unattempted **3-table** query. It's the foundational
next step: it exercises ADR 270's n-ary comma-join recognition **end-to-end on a real TPC-H shape under real
optimizer facts** (only a `cross_join_test` unit test covers 3-table routing today), and 3+-table joins gate
roughly fifteen of the remaining queries. Its Decimal arithmetic (`1 - l_discount`, `l_extendedprice * (…)`,
`SUM(Decimal)`) is already covered by the q01/q14 arc, so q03 adds the *join + grouping* surface without new
arithmetic.

q03 shape (tpchgen-2.0.2's bundled query text, `:1`/`:2` → literals; **no LIMIT** — see below):
```sql
SELECT l_orderkey, SUM(l_extendedprice * (1 - l_discount)) AS revenue, o_orderdate, o_shippriority
FROM customer, orders, lineitem
WHERE c_mktsegment = 'BUILDING'
  AND c_custkey = o_custkey AND l_orderkey = o_orderkey
  AND o_orderdate < DATE '1995-03-15' AND l_shipdate > DATE '1995-03-15'
GROUP BY l_orderkey, o_orderdate, o_shippriority
ORDER BY revenue DESC, o_orderdate
```

## Decision
Bring q03 into the gauge as a measured row in **both** modes; do **not** implement whatever wall it surfaces.

1. **q03 SQL, tpchgen-exact, no LIMIT.** Verified: tpchgen-2.0.2's Q3 text ends at `order by revenue desc,
   o_orderdate;` — it carries no `LIMIT`. The spec's "first 10 rows" is a presentation directive the reference
   query text omits, so the official-shaped q03 (our TPC-H source is tpchgen) has no `LIMIT`. It is also
   immaterial to the first wall — `Take` is the outermost op and already landed, while the expected wall is
   deeper — so omitting it costs no measurement value and keeps the attempt to the core 3-table grouped join.
   Same text both modes; only `lineitem` physical types differ (the q01/q06/q14 dev/strict discipline). Do
   **not** rewrite the query to dodge a wall.
2. **Fixtures (reuse the ADR 269 multi-table harness).** Add `customer` (`c_custkey`, `c_mktsegment`) and
   `orders` (`o_orderkey`, `o_custkey`, `o_orderdate`, `o_shippriority`) from `tpchgen`'s
   `CustomerGenerator`/`OrderGenerator`; **append** `l_orderkey` to the dev/strict `lineitem` fixtures
   (append-only, like ADR 269's `l_partkey`, so q01/q06/q14 column positions and digests don't move).
   customer/orders carry no decimals, so they're identical dev/strict (like `part`). Seed honest
   `TableOptimizerFacts` for all three batches via `run_query_with_tables` — q03 is its first 3-table user.
3. **Measure and classify precisely.** Run q03 dev + strict and record the row. Build the **full** q03 attempt
   (not a simplified probe) so the measured wall is the real first one. If it blocks, add a **specific**
   recognized blocker for the measured reason (ADR 262 precise-match) — not a generic surface bucket; if the
   reason is unrecognized, leave it `fail` (honest) rather than force-green; if it `pass@execute`, the board
   gains a fourth green query.

### Grounded wall shortlist (measured in impl — NOT pre-locked)
- **Most likely: GROUP BY over a join output.** q01/q06 group over a single scan; q03 groups
  (`l_orderkey, o_orderdate, o_shippriority`) over a 3-table join with keys from *different* tables. That
  key-resolution-across-the-join is the plausible new wall.
- **Probably not the wall** (grounded): the 3-table comma join — ADR 270's recursive routing lifts
  `c_custkey=o_custkey` and `l_orderkey=o_orderkey` left-deep (unit-tested for 3 tables); and **ORDER BY
  revenue DESC** — the planner has aggregate-output sort machinery (`aggregate_output_catalog` +
  `add_hidden_sort_projection`, `sql_planner.rs:3495`). Literal date bounds avoid `INTERVAL`.
- **Not q03's concern:** correlated scalar subqueries are a hard reject (`sql_planner.rs:9388`) — that's the
  q04/q17/q20/q22 frontier. q03 has no subquery.

The honest expectation is a GROUP-BY-over-join wall, but the **impl measures** and the measured reason is the
deliverable.

## Watch-items (operator) → guards
- **No engine feature.** Nothing is added to make q03 pass; strict stays `Decimal128`; q01/q06/q14 rows and
  digests are unchanged (appending `l_orderkey` must not reorder existing columns).
- **Classify what you measure.** A blocked row is green only if its reason is *recognized and specific*; an
  unrecognized reason is `fail`, not a forced green (the harness honesty rule).
- **`status` stays static capability inventory** (q03 → `implemented`); the measured pass/blocked lives only in
  the JSONL-backed matrix.
- **No LIMIT / no top-N surface** in this cut (tpchgen-exact); a dialectal top-N would be a separate surface.
- The verify-first full-q03 attempt is kept as a grounding regression.

## Acceptance
- q03 moves `not_run` → a measured row in **both** modes; the matrix and a harness test render it.
- If blocked, the measured reason is allowlisted with a precise classifier and **names ADR 273**; if `pass`,
  the board gains q03 green without adding a blocker reason.
- q01/q06/q14 unchanged; `status` inventory unchanged in shape.

## Forward arc
The measured q03 wall names ADR 273 (likely GROUP-BY-over-join, else whatever it measures). Then the rest of
the multi-table frontier (q10 4-table, q05 6-table — the stronger n-ary stress), and as separate arcs the
**correlated-subquery** family (q04/q17/q20/q22) and **date-interval arithmetic** (q04's `+ interval '3'
month`), both of which q03 deliberately avoids.

## Why toron-home
The `toron-tpch` reachability gauge and whatever binder/exec wall it surfaces. No cross-ring surface.
