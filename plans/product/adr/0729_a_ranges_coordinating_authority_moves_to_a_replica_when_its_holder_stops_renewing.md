# ADR 0729: a range's coordinating authority moves to a replica when its holder stops renewing

Status: accepted as a design, 2026-11-13 (Claude, Codex). Defect DC-224. Source conclusion and one characterization run accepted by Codex 01a1d61x; design cleared for implementation by Codex 01a1d63x after two held drafts (`reviews/dc224-20261113/`: ADR-DRAFT-r1, r2, ADDENDUM-1, CODEX-01 to CODEX-05). ParentDecisions mode only.

## Why
- In this mode a new write to a range is coordinated only by the range's lineage holder. A lineage is granted only to the range's ring primary. Reserve requires the holder to be each segment's first replica. Commit requires the holder's own acknowledgement. Placement is sealed (ADR 0720). Nothing closes a lineage when its holder merely stops.
- So while a range's primary is stopped, no new write to that range commits, whoever leads the control ring. Run once, test only: with the control leader unchanged and a majority up, 72 of 72 attempts over 9 s answered NOT_LEADER naming the stopped node, nothing was reserved, a range with a live primary took writes, and the same write identity committed when the primary returned (bigfoot `~/work/reviews-logs/dc224-dev/c1.log`, sha256 0c128c0f…).
- ADR 0700 lists failover availability among what it covered. That held only when the stopped node was not the written row's primary: the three-node workflow stops whichever node leads Raft and then writes one fixed row. This ADR records that limit beside that claim; ADR 0700 is not edited. No figure for how much of the ring one node is primary for is claimed.

## What stays fixed
Replica placement (the sealed membership and the ring's segments); the commit rule (a majority of the child's plan that includes the child's recorded holder); every recorded claim and outcome; reads (they use the ring's Accepted inventory at a cut and prove or repair each child from its plan, and consult no holder); generation reports (from the epoch's peers); Today mode and every lease structure the two modes share.

## Decision

### 1. Tenure
A lineage is `{range_end, epoch, holder, incarnation, generation, floor_ms, protected_until_ms, first_grant_pending}`. Its tenure is `(range_start, generation)`. One lineage entry exists per range, so there is never a second live authority over it.

A generation begins in three ways, each installing a floor (item 4):
- a grant where no lineage exists for the range: only by the range's ring primary (unchanged);
- a regrant by the lineage's holder after its lease lapsed (unchanged: today's gap boundary, which closes that holder's orphaned Reserved parents so it can resolve them);
- a takeover (item 3): the holder changes.

A generation ends by a takeover, a regrant after a gap, or a prune (epoch change, or the holder's incarnation superseded; unchanged).

### 2. Leases follow the tenure and name it
- The mode's lease batch (`AcquireLeases`, a mode-only command and frame) carries, per range, `expected_generation: Option<u64>`, and once per batch the `stamp_ms` of item 4.
- A grant by the lineage's holder H at its current incarnation naming the lineage's generation is exactly one of:
  1. **renewal**: an unexpired continuing lease is on record; the tenure continues; the expiry never shortens (unchanged);
  2. **the takeover's first grant**: the lineage has `first_grant_pending`; the tenure continues at the takeover's generation, the lease is recorded, the flag is cleared. Once per takeover;
  3. **regrant after a gap**: neither of the above; a new generation for the same holder with a new floor.
- Where no lineage exists, only the ring primary's grant naming no generation is admitted.
- Everything else is denied with nothing changed: the ring primary asking for a range another node holds; a request naming an earlier generation (a delayed message from an earlier tenure, including of the same node); a request with no generation where a lineage exists. A denied request cannot clear `first_grant_pending`, shorten protection, or touch the tenure.
- In this mode the single `AcquireLease` and the unqualified `ReleaseLease` are denied before any effect. `ReleaseLease` names no generation and has no production sender; a tenure-bound release is not added. Today's behaviour and the shared structures are unchanged.
- A takeover removes the old holder's applied lease record, so the generic overlap sweep never meets it.

### 3. Takeover: one log-ordered command
`TakeOverLineage { range_start, generation, successor }`, a decision command signed by the successor's bound key and carrying the entry's replicated leader stamp. It is admitted when all hold:
1. the lineage at `range_start` exists with exactly `generation`, and `successor` is not its holder;
2. the store is sealed, the epoch's placement is the sealed one, and no unfinished migration touches the range;
3. the supported shape holds (item 8), and `successor` is a data member of the sealed placement at its current incarnation with a bound key, and in the replica set of every ring segment the range intersects;
4. **lapse**: with `now = max(clock_ms, stamp_ms)`, `now > protected_until_ms`, and either no lease is on record for the range or `lease.lease_expiry.physical_ms + TAKEOVER_GRACE_MS < now`.

Effect, atomic, with checked arithmetic (an overflow is a refusal): `clock_ms = now`; the lineage becomes `{holder: successor, incarnation: its current one, generation: next_generation, floor_ms: now + LEAD, protected_until_ms: now + the protection, first_grant_pending: true}`; `next_generation += 1`; the range's lease record is removed.

- Two takeovers of one generation cannot both apply.
- `protected_until_ms` covers the successor before its first grant, and gives a finite rule if it dies first: the range is takeable again once protection has passed.
- **The lapse is the trigger, not the fence.** Every way a holder makes something committed goes through the ring: Reserve checks that each child's lineage is open, and Finalize, Resolve and Abort conclude a still-Reserved parent whose bound lineage closed as refused before reading any evidence. A wrong lapse judgement therefore costs the live holder its pending parents, as definite refusals; it cannot commit conflicting data.

### 4. Ordering: a floor on every generation
- A claim's commit HLC is chosen by its coordinator from an in-memory clock; the reducer bounds it only above, by the entry's stamp plus `DECISION_COMMIT_HLC_LEAD_MS` (LEAD). Version order within a key is the full HLC, greatest wins, in reads, in delete and no-op selection and in the certified base. One commit HLC covers every child of a claim.
- `clock_ms` is the ring's own clock: every admitted Reserve, RecordNoop and AdvanceFloor sets it to `max(clock_ms, stamp)`, and it is part of the snapshot. A raw leader stamp is not monotone across leaders; `clock_ms` is. So at any entry every claim admitted earlier has `commit_hlc.physical_ms ≤ clock_ms + LEAD`.
- Whenever a generation begins, `floor_ms = max(clock_ms, stamp_ms) + LEAD`, and the entry sets `clock_ms` to that maximum. Nothing in apply reads a wall clock:
  - a takeover's stamp is its decision entry's;
  - a lease batch's `stamp_ms` is supplied by the control leader that builds the entry, from the same gated clock decision entries use: the leader itself for its own ranges, and the leader's handler for a follower's forwarded request. A batch that begins no generation ignores it.
- Reserve of a **version-producing** claim (a write, or a delete, whose tombstone has a commit HLC) requires `claim.commit_hlc.physical_ms > floor_ms` of every lineage it binds; otherwise the refusal `BelowTenureFloor`, retryable. A delete's existing `commit_hlc > winner_hlc` check stays.
- RecordNoop has no commit HLC, publishes no version and concludes as a no-op: the floor does not apply to it and it is unchanged. Its selection is evaluated at an applied leader cut over the Accepted inventory with proof or repair, and its reducer check names the current lineage, not the ring primary.
- The coordinator reads the floors of the lineages its claim binds from applied state before stamping, and merges its clock with `floor + 1` through the existing merge. Two call sites change: the write coordinator and the delete's tombstone clock.
- **What the floor proves:** every version reserved under a generation orders after every version reserved before that generation began, whoever held the range. **What it does not:** order between two claims of one generation, which rests on the holder's in-memory clock and is reset by a restart inside an unexpired lease (DC-233, open, not fixed here).

### 5. Who proposes
Eligibility is the reducer's, from committed state. Proposing is local and cannot veto: each eligible replica's lease pass proposes a takeover of a range once it sees the lapse on its applied state and clock, after `index × TAKEOVER_STAGGER_MS`, `index` being its place among the segment's replicas after the holder. A stopped earlier candidate delays a later one by a step, never indefinitely. The generation check arbitrates concurrent proposals.

Constants: `TAKEOVER_GRACE_MS = 2 × MAX_OFFSET_MS`. The protection is the lapsed lease's own recorded duration, clamped to 1 s to 60 s, or 3 s where no lease was on record: a committed input, since the reducer does not know a node's configured TTL. The stagger is a third of the proposing node's configured lease TTL per place.

### 6. What a superseded holder can still do
- It can still append provisional rows and intents locally, send them to replicas, and collect signed acknowledgements for a parent reserved before the takeover: a replica checks the recorded claim and not the lineage, the holder does not re-read its lineage between append and signature, and a lagging store passes every check against stale state.
- Nothing it writes or collects after its generation closed can become newly Accepted (closure is checked first; a closed generation never reopens), and nothing of a parent not recorded Accepted is served to a read, a delete or no-op evaluation, a repair, or the certified base.
- Each store marks such intents refused from the applied record; the rows go when a certified generation erases the parent. The parent is driven to its refusal by the node now holding the lineage over its coordinator child's range, through the existing resolve path.
- A parent already Accepted keeps its outcome whatever happens to its lineage.
- Residual, not fixed here: late bytes occupy storage until erased; DC-234 (a late append across an erasure and base activation; cleanup of secondary-index rows appended with provisional rows) is open and not shown to affect serving. If implementation finds either does, work stops and that dependency is named first.

### 7. Reserve, routing, readiness, hand-back
- Reserve drops "the holder is the segment's first replica". It keeps: the lineage open for the named holder, the holder in the plan, the plan equal to the segment's replicas at current incarnations, and the floor.
- The lease requester asks for every range whose lineage this node holds, plus its primary ranges that have no lineage. The control leader validates a forwarded request by the same rule. Readiness requires every range this node holds to be leased; a primary range another node holds is not a failure.
- A node redirects a fresh request only to the holder of the lineage covering the request's own first position, and only while that lineage has an applied lease of its own (its range, its holder, the current epoch) not past its expiry by the grace on the node's clock; a lease the same holder has over another range does not count. A Reserved parent is redirected to its recorded coordinator only while that coordinator's recorded lineage is still open and leased likewise. Otherwise the answer is the existing retryable stall, which names no node; a Reserved parent is never reported refused before its recorded refusal. Writes, KV writes and deletes, fresh and resumed. A routing judgement; it decides nothing. No new wire status.
- Unchanged: table, KV and delete coordination and the no-op already take the coordinator from the lineage; child roles, Finalize, Abort and repair take the holder from the recorded claim; reads need plan membership only.
- No hand-back. The returning primary holds no lineage for the range, is denied grants for it, redirects, and serves as a replica. Authority moves again only by a takeover.

### 8. The supported shape
- All-data-replicas: every tenant's replication factor is at least the number of data members of the sealed placement, so every segment's replicas are all data members. Any node count.
- A takeover is refused unless that holds for every tenant on record. Authority over a range in an unsupported configuration is not promised to move.
- Tenant creation checks nothing about the factor today beyond non-zero, so this is a real admission change in this mode: creating a tenant whose factor is below the data member count is refused, before any tenant or keyset state changes, while any lineage is held by a node other than its range's ring primary. A factor at or above the count is accepted: it cannot disable a later takeover. No path that changes an existing tenant's factor exists; none is added.
- Lineage splitting, which smaller factors would need, is not added.

### 9. Formats and the wire
- One decision command, two refusals, lineage fields, the batch's stamp and per-range generation: the ParentDecisions WAL, snapshot, marker and Raft/decision envelope are bumped in place; earlier stores and peers are refused.
- The lease batch request and response frames carry general envelope 1 today and are outside the decision envelope family. Their body changes, so they join that family at the new version: the server checks mode and version before decoding a request, the client before decoding or caching a response, and the generic reader's acceptance of envelope 1 does not bypass either. A retired peer refuses the new body; a new peer refuses the old one. General frames and Today's lease messages are unchanged.

### 10. The client reaches a node that answers
Added after the first real three-daemon run failed (validation record): moving authority is of no use to a client that is waiting on the node that lost it.
- Until the old holder's lease lapses, a live node correctly redirects to it; it cannot know the holder stopped. The public client then asked that node for the cluster's status and dialled it for the write, and neither wait had a bound of its own: the operation's deadline travelled on the wire and bounded nothing locally.
- **One caller deadline over the whole call**, for a table write and a table delete: the first connect, every refresh, every backoff, and the wait for an answer. A step is cut where it stands when the deadline is reached. With no deadline, the wait for an answer after a request was sent is as before: unbounded. The first connect is not: see the next point, which supersedes an earlier version of this decision that left a deadline-less first connect unbounded.
- **Every node gets a finite budget before anything is sent to it** (one second), with or without a caller deadline, however it was chosen (a hint, the leader the client remembers, a replica from the topology, the call's first node included), at each step that asks it: its turn in a topology refresh, and the connect and stream open of an attempt. The budget is a policy for moving on, not failure detection. It never outlasts the caller's deadline and never adds to it. A hint-only budget was not enough: a call that ends on its last redirect leaves that redirect's node remembered as the leader, and the next call began there with no budget (the third real three-daemon run's second call, reproduced by a client test). A node that refuses the connect at once is handled as one that stays silent: the attempt is spent and another node is asked. A failed connect is never an acknowledged write, and asking another node bypasses no peer verification and no server authority check. When no node is left the call ends with the last node's own error, and when the attempts end first, with the local exhausted stop below.
- **A node is not asked the same thing twice by a call, and the two things are separate.** A node that did not answer a topology refresh is not asked for a refresh again by that call; that says nothing about a mutation, so a hint to it is still followed, in a budget of its own. A node whose own mutation connect did not give a stream is not asked again by that call, for an attempt or for a refresh. The call then asks where it would with no hint: the control leader when it is one of the row's replicas, else the first replica, skipping the nodes whose mutation connect failed. That node is only another place to ask: it coordinates, redirects or stalls by its own authority checks. Neither list is an authority fence, a membership change or an operation outcome.
- **Attempts are not refunded.** A redirect is an attempt, a node's connect that gave no stream is an attempt, and the request that follows is the next. A hinted node that failed the refresh is still dialled for the attempt: a node that answers neither gets two bounded tries in a call, one for each purpose, never a third.
- **Knowledge.** Every attempt carries the same operation identity. A stop the client decides itself (its deadline, or its last attempt spent on a node that gave no stream) reports the operation's outcome as indeterminate, always: a call knows only its own attempts, the identity may be one an earlier call already submitted, and a call that reached no node has no evidence about that. Precision is given up even for an identity that is in fact fresh. The attempt in flight at a deadline is dropped locally, not detached, and nothing is claimed about the server. Exhaustion decided from the call's answered attempts keeps its earlier rule and its recorded cross-call limitation (DC-215). The local stops use the existing statuses and reasons; no wire status is added.
- **A bounded refresh asks no skipped node**, whatever list it would come from, the topology source's own bootstrap peers included; an empty candidate list means the source's own peers, still without the skipped ones.
- **Scope.** The client's table write and table delete, and the topology source's bounded refresh entry point (whose default asks as before and is bounded only by the caller's deadline). The transport providers, Raft, and every other client operation are unchanged.

## Algebra
- Authority key: (range_start, generation), one holder per key; a generation is consumed by the first event that ends it.
- A commit needs, per child, a majority of its plan including its recorded holder at its recorded generation, and that generation still open at the deciding entry.
- Quorums come from the plan's length; nothing assumes three.
- Version order: full commit HLC. Across generations of a range it is enforced by the floor; within one it is the holder's clock.

## Limits, stated
- **Time.** The lapse compares a lease expiry the holder requested (the leader clamps the TTL, not the requested start) with the ring clock. A recovery time of about one TTL plus the grace assumes request clocks within the clock gate's bound; a future-dated applied lease delays eligibility beyond that. Likewise a new generation's first Reserve needs a leader stamp above the historic `clock_ms`; the gate bounds present disagreement, not how far a historic high-water sits above wall clocks after clocks moved backward, so such writes stall with a retryable refusal until wall time catches up. No clamp on grant time is added, and no guarantee is made for arbitrary clock jumps.
- **The client.** Not changed: redirects in reads, queries, blob writes and counters; a call with no deadline whose first node never completes a connect or never answers; the transport's own idle timeout. A call made inside the lapse window is still redirected to the stopped holder and, with three attempts, can end as attempts exhausted before authority has moved: the caller offers the same operation again.
- No hand-back policy; no lineage splitting; no membership or placement change; DC-233 and DC-234 are not fixed.
- **Authority does not rebalance.** A node down past its lease, the grace and its range's stagger can have its ranges taken by whichever eligible survivors propose first, and gets none of them back on return. Coordination work follows authority; replica placement and data do not move. Where authority ends up after several outages depends on which survivors took each range; nothing evens it out. Returning authority is a later policy.
- Generation certification still waits for every member's report: with a node down, generations do not advance and reclamation waits, as before.

## Acceptance
1. Reducer and format tests, each named for its rule: the three grant cases and every denial; takeover admission (generation, lapse, grace, protection, eligibility, shape, seal) and its effect; protection, then a second takeover; the floor (a leader stamp below the ring clock, a takeover, a regrant after a gap, a claim spanning two lineages; overflow refusals); the renewal race both ways; terminal outcomes unchanged and still-Reserved parents refused and resolvable by the successor after closure; the tenant factor guard; the state's round trip; the mode's golden bodies, of which exactly two moved; refusal of the earlier marker, envelope and lease-batch envelope.
2. A cluster test: a primary stopped with the control leader unchanged; the earlier candidate in the range's replica order unable to act; the later one takes the range; the write that could not be reserved commits under it; a range whose primary is live is unaffected throughout; the returning primary holds no lineage for the range, redirects, and a write entering at it commits; every node restarts on its own store and the range is still the successor's.
3. A cluster test with barriers, the old holder running and cut off from its leases: one write held before its claim is built, one held before Finalize with its children's acknowledgements already gathered (nothing in this test is written after the takeover), one accepted earlier; after the takeover the reserved one is refused once and for good, the unreserved one commits under the successor with the same identity, the accepted one is untouched, and no node reads the refused write's rows.
3a. A cluster test: a successor that never stored an accepted row (it refused its copy; the primary and the other replica accepted it) takes the range and deletes the row: it repairs the row from the surviving replica, selects it, publishes a tombstone above the new generation's floor, and a second delete records a no-op under its lineage; no node reads the row.
3b. Two routing unit tests: a redirect follows the lease of the request's own range, not the holder's other ranges; a Reserved parent is not routed to a coordinator whose lineage closed.
3c. Client tests on scripted nodes with a connect that never completes: a hinted node's connect does not consume the call; a first node's connect, with a caller deadline and with none, gets its budget and the next node answers; a first node that refuses at once is skipped for the next; when no node gives a stream the call ends with its attempts, indeterminate; a node remembered from one call's last redirect does not consume the next call of the same identity (fails on the hint-only version by running to the deadline, the real run's answer); a hinted node that answers neither a status request nor a connect gets one bounded try for each; a hinted node that fails a status request and answers the write is asked for the write and commits it (the real three-daemon run's shape: with one shared list the call spent its attempts on the redirecting leader and never asked the holder); the caller's deadline ends the call when it is shorter than the hinted budget, when the first node or a topology source is pending, and when a sent request is never answered, each time reported indeterminate; a second call with an identity an earlier call may have submitted, reaching no node, does not claim the operation did not commit; an unreached node neither sets nor clears what an earlier answer left open; a bounded refresh never asks a skipped node, even from its bootstrap peers. Seven of the first nine written fail on the earlier client by never returning; the status-failure test fails on the one-list version of this client with the real run's answer (attempts exhausted, the holder never asked).
4. The three-node workflow, both variants, and the 2 MiB worker regression pass in one whole-crate run; the real three-daemon test passes once with a non-leader primary stopped and a write to its range.

Covered at the reducer only, not by a cluster: a parent spanning two ranges of which one is taken over. Not covered: rows a superseded holder writes after the takeover applied elsewhere (DC-234 stays open); a partition (the cut-off holder is modelled by withholding its lease requests, not its network).
