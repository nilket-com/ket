# ADR 0737: ADR numbers are sequential within their own directory

Status: proposed (2026-11-15 UTC); strict order and the subject grammar chosen by the operator. Supersedes ADR 0639's numbering rule only ("New ADR numbers are repository-wide starting at 0630", and its ">=0630, repository-wide unique" check). ADR 0639 is not edited; its subject, body, plan-shape, size, count and evidence rules stand. Lands after product 0736 (the database team's backup plan, 93851467d), which keeps its number.

## Why
- The repository holds several ADR sequences, one per ADR directory: `plans/product/adr` (to 0735), `nilket/crates/toron/plans/adr` (0001 to 0629), `nilket/crates/wendelon/plans/adr` (0001 to 0102) and `crates/libaryon/plans/adr` (0001 to 0011). Each began at 0001; 0012 exists three times.
- ADR 0639 continued one shared sequence from 0630. It did not start fresh: toron's own sequence had reached 0629 (2026-10-03), so the product directory jumped from 0176 to 0630 and 0177 to 0629 never existed there. Most of product's 0630 to 0735 are database decisions filed under product, and a crate's next decision gets a product-sequence number.
- The operator's rule is that ADR numbers are per directory and sequential.
- The checker identifies an ADR by its number alone in four places: plan resolution (any same-number document anywhere in the tree), implementation counting (every first-parent `impl: adr NNNN` subject), count exceptions (`impl_limits` keyed by number) and numbered docs (any same-number document). Once numbers repeat across directories, each can bind a commit to the wrong decision.

## Decision
1. **A decision is (directory, number).** An ADR directory is `plans/product/adr` or any `<prefix>/plans/adr`; its documents are regular files named `NNNN_<slug>.md` or `NNNN-<slug>.md` (`_evidence` files excluded). The decision keeps its identity when its file is renamed or amended.
2. **Subject grammar.** `plan|impl|docs: adr NNNN {name}? terse summary`. The optional name, right after the number, names the directory: `product` for `plans/product/adr`, otherwise the directory holding `plans/adr` (`libaryon`, `toron`, `wendelon`). A first summary word that names an ADR directory present at the commit is the qualifier, and a terse summary must follow it. Without a qualifier, the number must be held by exactly one directory at the commit; otherwise the commit is refused and the error names the choices. Example: `plan: adr 0012 libaryon content-aware table column widths`. Long explanations go in the Markdown, not the subject.
3. **A plan's document is its one changed file.** A `plan: adr NNNN` commit adds or amends exactly one ADR file numbered NNNN (unchanged rule); the file must be a regular file at the plan commit, and its directory must be the subject's decision. A plan whose file is not a regular file authorizes nothing, even after the file is later replaced.
4. **A new number is the next in its directory.** For a plan that adds its document, the directory's numbers at the plan's first parent decide: the largest plus one, and 0001 in a directory with no ADR yet. A number already present, a skipped number, a backfilled lower number and 0000 are refused. When two plans in one directory race, the one that lands second renumbers before it is pushed. The same number in different directories is not a conflict.
5. **No commit may join two documents with one number in a directory.** Each plan is checked against its own first parent, so two branches can each add a valid `0012` to one directory and a merge then holds both. Every checked commit, merges and non-plan commits included, is refused if it holds two or more ADR files with one number in one directory that its first parent did not hold as exactly that set. Existing duplicates a commit leaves unchanged are not re-judged.
6. **Implementations and numbered docs.** An `impl` or `docs` commit resolves its decision from its subject (item 2), then needs: exactly one regular file for that decision at the commit (a tree, link or submodule with its name is not one), and an earlier plan in first-parent ancestry whose changed file is in that directory with that number. A later malformed plan of the same decision does not unbind it; there is no binding to another directory.
7. **Counts and exceptions follow the decision.** The five-implementation limit counts the first-parent `impl` commits whose subjects resolved, at their own commits, to the same decision. Another directory's implementations of the same number are not counted; renaming or amending does not reset the count. `ci/commit-subject-allowlist.json` schema 2 keys `impl_limits` by `directory` and `adr`; an exception for one decision does not apply to another with the same number. `oversize` entries stay path and blob.
8. **Schema transition.** The gate runs the checker from its own checkout and reads the policy file pinned at the candidate, so the new checker meets candidates that still hold schema 1. A schema 1 file is accepted when its `impl_limits` is empty (today's state: nothing keyed by number to reinterpret); a schema 1 file with a count limit HOLDs, as does a schema 2 entry not keyed by directory and number. The checker and the schema 2 file land in the same implementation commit.

## Limits, stated
- An implementation committed before this ADR whose subject was ambiguous at its own commit resolves to no decision and is not counted. Only the checked range is judged.
- A summary whose first word happens to be an ADR directory name is read as a qualifier.
- Strict order means two plans prepared at once in one directory cannot both keep their numbers; the second to land renumbers (file and subjects) before its push. Main formerly landed reserved numbers out of order (0722 before 0721); that is no longer accepted.

## What does not change
Message prefixes; no bodies; author and committer identity; a plan changes one ADR file and nothing else; the 400-line bound and its path/blob exceptions; evidence-only implementations refused; side-branch commits checked; shallow, missing and non-ancestor bases HOLD. Existing documents keep their numbers and paths. Where a decision belongs (product or crate) is not decided here.

## Acceptance
`ci/test_commit_subjects.py` (isolated temporary repositories), 58 controls, including:
- numbering: the next number passes; a lower, duplicate, skipped or carried number fails; out-of-order landing fails; a new directory starts at 0001, and 0000 or 0002 fails;
- integration: a merge joining two same-directory documents with one number fails at the merge; one number in two directories through a merge passes; a non-plan commit adding a duplicate fails; an unchanged legacy duplicate is not re-judged;
- identity: an ambiguous unqualified plan or implementation fails and a qualified one passes; a qualifier naming another directory than the plan's file fails; a directory name with no summary after it fails for plan, impl and docs, while a one-word unqualified summary passes; a link as a plan document fails, and a published link plan later replaced by a regular file does not authorize an implementation or numbered doc until a real plan amends it; two directories with one number keep separate counts, the earlier directory's five implementations asserted before the new plan and the new directory's sixth failing; interleaved decisions keep their own counts (a sixth editor implementation after another directory's plan fails) and numbered docs bind by qualifier; a count exception does not transfer; renaming then amending does not reset the count; deleting the decision's file, or replacing it with a directory of the same name, fails both an implementation and a numbered doc; a malformed later plan does not unbind; a side-branch implementation binds through its own first parent and an implementation after the merge on main does not see the side plan;
- schema: schema 1 with no count limits passes; schema 1 with a count limit HOLDs; a schema 2 entry keyed by document HOLDs.

Through the public entry point (`python3 -B ci/commit_subjects.py --repo . --commit <ref>`), run by the implementation's checker: the composed candidate (the database team's 93851467d, then this branch's commits rebased onto it, with the schema 2 file) PASS, recorded at delivery.
